# MAX: пилот на событии готовности JSON

Пилот выключен по умолчанию. Единственный маршрут — готовый JSON
`equipment-tasks/T-….json` → штатный S3 poller/outbox → существующая очередь
`xtrek_s3_events` → `tasks.process_s3_event` на любом действующем worker.
Новых очередей, задач Celery, workers и служб не требуется.

В MAX отправляется тот же HTML-текст, что и прежним notifier:
`Задание: T-….json` — ссылка на существующий S3-файл. Превью отключено,
`notify=true`, вложений нет. Совместимость тела запроса и параметров
проверяется сравнением с фактическим старым notifier. Дополнительных
объектов S3, реестра доставок и чтения истории MAX нет. Ссылка действует
48 часов; для версионируемого объекта фиксируется VersionId.

## ACK и повторы

Только успешный ответ MAX с MID завершает задачу и допускает ACK.
MID, ID задания, номер попытки внутри текущей доставки и задержка
записываются в локальный лог. При ошибках повторяется только подготовка
ссылки/уведомление; бизнес-маршруты заказа не вызываются.

До пяти попыток выполняются внутри той же задачи с паузами 5, 10, 20 и
30 секунд. `self.retry` не используется, замена события не публикуется.
После пяти ошибок или некорректной конфигурации/входных данных worker
ждёт 60 секунд и делает `Reject(requeue=True)` для исходного события.
Такое событие сохраняется и после восстановления может попасть на любой
worker. Лимит пяти попыток относится к одной доставке, не к сроку жизни
задания. При падении дочернего worker используется существующий
`task_reject_on_worker_lost=True`.

Это занимает один слот общего пула во время ожидания. Пилот следует
ограничивать небольшой группой новых ID и контролировать задержку других
задач. При массовом сбое или неисправимой конфигурации возможны повторные
попытки до исправления причины. Выключенный пилот с сохранённой группой
также удерживает события: пауза и requeue, без отправки. Исключать
неразобранные ID из группы допуска нельзя: это может разрешить старый
маршрут. Возможны дубли после принятого MAX сообщения с потерянным ответом;
оператор/SCAN обнаруживает такие случаи. Локальные логи не дают полного
учёта дублей при потере ответа.

## Допуск только новых заданий

Файл `XTREK_MAX_QUEUE_PILOT_COHORT` поддерживает два режима.

Для небольшой партии с заранее известными будущими ID:

```json
{"not_before":"2026-11-10T00:00:00Z","keys":[]}
```

Для реальных новых заданий, UUID которых заранее неизвестны:

```json
{"not_before":"2026-11-10T00:00:00Z","mode":"new_after_cutoff","excluded_keys":["equipment-tasks/T-example-old.json"]}
```

Даты и ID выше — примеры. Автоматический режим допускает неизвестные ранее
ключи только после временной отсечки. Poller и старый notifier используют
одинаковый фильтр по ключу, исключениям и LastModified. Worker дополнительно
проверяет первоначальную дату внутри JSON. Старые исключённые ID не
попадают в новый маршрут даже при перезаписи с новой датой. Объекты заданий
должны оставаться неизменяемыми; перезапись нового, уже отправленного ID
создаёт новое событие и может привести к повторному уведомлению.

Перед автоматическим включением нужно:

1. Приостановить штатную публикацию событий, завершить текущие задачи
   workers и остановить старый notifier между доставками. Сохранить откат
   и снимок состояний uncertain. Не создавать дополнительные обработчики.
2. Собрать `excluded_keys` из **всех** существующих equipment-tasks JSON,
   всех известных ID старого notifier (включая uncertain, manual_review,
   ручные подтверждения и конфликты) и прежних событий equipment-tasks
   в outbox. Это неизменяемый снимок исключений при переключении, а не
   журнал дальнейших доставок. Пустой список допустим только на пустом стенде.
3. Зафиксировать новую UTC-отсечку после завершения снимка, установить
   одинаковый файл на всех участниках и сверить его хеш. Затем включить
   workers, штатный poller/publisher и прежний notifier. Полный список
   исключений и отсечка не должны изменяться при обычном перезапуске.
4. Не переносить исторические объекты, не менять их даты/теги ради допуска,
   не восстанавливать старые события и не возвращать допущенные новые ID
   прежнему notifier при откате. Старые uncertain остаются вне нового
   маршрута; их состояние и число попыток не изменяются настройкой пилота.

Первоначальная дата JSON и LastModified проверяются относительно отсечки.
Режим с точными ID также сохраняется: перед созданием партии убедиться,
что этих ID нет в S3, старом ledger и outbox; не переиспользовать ID.

На poller, workers и старом notifier должен быть один и тот же защищённый
файл допуска. Worker фиксирует список маршрутов при запуске; менять
группу на работающем парке нельзя, нужна согласованная перезагрузка
конфигурации. Старый notifier исключает эти точные ключи до первого
создания пилотного объекта. На workers дополнительно нужны:

- `XTREK_MAX_QUEUE_PILOT_ENABLED=1`;
- `XTREK_MAX_PILOT_BOT_TOKEN`;
- `XTREK_MAX_PILOT_CA_FILE`.

Используются существующие S3-настройки worker. Секреты не передаются в
событии и не записываются в лог. Без файла допуска пилот не влияет на
обычные маршруты.

## Выпуск и откат

Разворачивать только полный main после отдельного согласования выпуска.
Сначала одинаковые версии и допуск на всех участниках, затем новые файлы
в штатном маршруте. Проверить работу ссылки в SCAN до реальной партии.
Пилот не устраняет зависимость существующего брокера/poller от 94.

При откате прекратить допуск новых ID, сохранить исключения для уже
допущенных и разобрать ожидающие доставки. Не возвращать их автоматически
старому notifier и не переотправлять старые uncertain. Завершать текущие
задачи перед перезапуском, сохранять конфигурацию и возможность отката.

## Изолированные тесты

`tests/test_max_queue_pilot.py` проверяет формат, допуск и чтение S3.
`tests/integration/test_max_ready_event_rabbitmq.py` использует настоящий
RabbitMQ, Celery и локальный HTTP-имитатор MAX. Интеграционные тесты по
умолчанию пропускаются. **Стенд одноразовый: тесты удаляют свою очередь.**
Никогда не направлять его на production. Требуются loopback `127.0.0.1`,
порт 25672, отдельный vhost `pilot`, синтетический пользователь `pilot`.

```sh
docker run -d --name xtrek-max-test -p 127.0.0.1:25672:5672 \
  -e RABBITMQ_DEFAULT_USER=pilot -e RABBITMQ_DEFAULT_PASS=isolated-test-only \
  -e RABBITMQ_DEFAULT_VHOST=pilot rabbitmq:4-management
XTREK_TEST_RABBITMQ=1 PYTHONPATH=.:tests \
  pytest tests/integration/test_max_ready_event_rabbitmq.py -q
docker rm -f xtrek-max-test
```

Дождаться готовности брокера перед pytest. Тесты не требуют реального
MAX-токена. Реальная проверка выполняется только отдельно в согласованном
тестовом чате, с лимитом одной отправки и GET по конкретному MID.

## Расхождение времени JSON и S3

Дата JSON и время готовности объекта S3 должны оба быть не раньше отсечки.
Дата JSON может опережать LastModified S3 не более чем на 5 секунд: часы
создателя и Object Storage различаются, а HEAD возвращает целые секунды.
Исходные даты не переписываются и не округляются в событии. Больший разрыв,
объект с LastModified в будущем и любой исторически исключённый ID удерживаются
до POST. Эта проверка одинакова при подготовке ссылки и перед отправкой.

Изменение относится только к текстовым уведомлениям готовых equipment JSON.
Доставка паллетных ярлыков и терминальных ошибок использует свои механизмы.
