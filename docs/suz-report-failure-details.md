# Подробные причины отказа СУЗ по сохранённому reportId

Проверено 14.10.2026 в 10:05 МСК на промышленном `https://suzgrid.crpt.ru`.
Подробности доступны через публичный API СУЗ: сначала квитанция, затем
связанный с её событием документ результатов обработки. Повторная отправка
отчёта для диагностики не нужна.

## Автоматическое получение в xTrek

`update_utilisation_report_status` (CLI `--utilisation-status` и обработчик
`utilisationReceipts`) при `reportStatus=FAILED` выполняет описанные ниже GET-запросы
с тем же клиентом СУЗ и сохраняет результат в поле `failureDetails` существующего
файла `utilisation_reports/<order_id>.json`. Дополнительных настроек не требуется.
Авторизация и штатное обновление токена выполняются существующим клиентом;
режим read-only токенов ниже относится к разовому исследованию API.

Структура `failureDetails`:

- `state`: `complete` — все найденные документы результатов прочитаны;
  `partial` — прочитана часть документов; `unavailable` — документы пока не получены;
- `receipts`: исходные квитанции со всеми событиями;
- `documents`: `resultDocId`, `docId`, `operationType`, массив `cisList` с `cis`,
  числовым `code` и необязательным `description`;
- `issues`: стадия сбоя, идентификаторы документа и тип исключения/HTTP-статус.
  Текст исключений не сохраняется, чтобы не переносить неограниченные тела ответов
  или секреты в журнал и файл статуса.

Сохраняются все записи КИ, включая `code=0` (успех). Документы начального события
`REPORT_UTILIZE_RECEIVED` не скачиваются. События `RNMS_GIS_ROUTED` с `docId`
также обрабатываются: причина отказа может находиться на стадии маршрутизации.

Завершённая диагностика повторно не запрашивается. Для `partial`/`unavailable`
следующий опрос снова получает квитанцию и догружает недостающие документы.
Уже сохранённые документы не теряются при временном сбое или конкурирующем
обновлении статуса с включённым `operation_state_path`. Сбой диагностики
не подменяет известный статус `FAILED` и не запускает повторную отправку.
`complete` означает полноту чтения доступных ссылок в квитанции, а не успешную
обработку отчёта или доступность данных Квитирования 1.0.

Журнал использует общий механизм `log_suz_diagnostic`, выделенный из прежнего
`_log_utilisation_error`: до 4096 байт JSON-экранированного тела — в журнал;
больший текст — в уникальный файл системного временного каталога
`xtrek-suz-error-*.txt` с правами `0600`, в журнале остаётся путь.
При ошибке записи в tmp большое тело в журнал не выводится.
Перед этим выводится ограниченная сводка: количество записей с ошибкой,
три наиболее частые причины (описания до 200 символов), число групп причин и путь
к сохранённому статусу. Все причины и КИ остаются в `failureDetails` и полном
временном файле. Временный каталог может очищаться операционной системой;
постоянным источником служит JSON статуса в настроенном хранилище.
При неизменной диагностике повторный опрос выводит только сводку,
чтобы не создавать одинаковые временные файлы на каждом повторе.

Большое поле исключено из `repr` модели статуса: стандартная печать результата
в обработчике также не выгружает весь список КИ в журнал. Ошибочные GET-ответы
клиента СУЗ используют тот же механизм ограничения и удаления секретов.

## Проверенная последовательность GET-запросов

Использовать исходный `reportId`, `omsId` из сохранённого ответа на отправку
и действующий токен СУЗ соответствующей организации и подключения.
Для всех трёх запросов заголовки:

```http
Accept: application/json
clientToken: <действующий токен СУЗ>
```

В xTrek токен выбирается по `purpose='suz'`, ИНН, `conid` и `oms_id`.
Не подставлять токен True API или `Authorization: Bearer`.
Для диагностики использован `TokenProcessor(..., tokens_read_only=True)`;
авторизация не обновлялась, настройки и реестр токенов не записывались.

1. Получить статус:

   ```http
   GET /api/v3/report/info?omsId=<omsId>&reportId=<reportId>
   ```

   Фактический ответ HTTP 200 для первого отчёта:

   ```json
   {
     "omsId": "58b959f7-2617-411e-a6ab-8581f3e21f61",
     "reportId": "5f6c1260-e851-420e-9991-a720decfd02d",
     "reportStatus": "FAILED",
     "type": "utilisation"
   }
   ```

2. Получить квитанции: в query-параметр **`resultDocId` передать `reportId`**.

   ```http
   GET /api/v3/receipts/receipt?omsId=<omsId>&resultDocId=<reportId>
   ```

   Ответ HTTP 200 — объект с массивом `results`. Для каждого элемента
   сохранять `resultDocId`, `sourceDocId`, `state`, `code`, `description`
   и весь массив `operations`. В четырёх проверенных случаях `resultDocId`
   совпал с `reportId`, `state=FAILED`, `code=1`, а описание было общим:
   `Document processing was failed`.

   Найти **все** события `operations[]` с
   `operationType="RNMS_GIS_PROCESSED"` и непустым `docId`.
   Для ошибок отправки на обработку также проверить `RNMS_GIS_ROUTED`
   с `docId`. Не брать первый `docId` без проверки типа события:
   у `REPORT_UTILIZE_RECEIVED` он обозначает исходный документ.

   Фрагмент фактического события первого отчёта:

   ```json
   {
     "operationType": "RNMS_GIS_PROCESSED",
     "docId": "46d1b02d-5fcc-4124-92e0-f6596c3f0b82",
     "details": {
       "state": "REJECTED",
       "productGroupIds": [35],
       "gtin": "04670404506857",
       "processed": 0,
       "total": 756
     }
   }
   ```

3. Получить документ по `docId` выбранного события и `resultDocId`
   содержащей его квитанции:

   ```http
   GET /api/v3/receipts/document?omsId=<omsId>&resultDocId=<resultDocId>&docId=<docId>
   ```

   HTTP 200 возвращает `content` **строкой, содержащей JSON**.
   Поэтому после разбора HTTP JSON нужен второй JSON-разбор:

   ```python
   envelope = response.json()
   document = json.loads(envelope["content"])
   for item in document["cisList"]:
       cis = item["cis"]
       code = item["code"]
       description = item.get("description")
   ```

   Сокращённый фактический ответ второго отчёта (один элемент из 606):

   ```json
   {"content":"{\"cisList\":[{\"cis\":\"0104670404506857215!4rt<\",\"code\":12,\"description\":\"Отсутствует карточка товара (GTIN) в НК\"}]}"}
   ```

   `cis` не содержит код проверки. `description` необязательно по спецификации;
   при его отсутствии сохранять числовой `code` и сверять справочник результатов
   обработки КМ (§ 5.3.1.18). В примерах PDF встречается `cislist`, но таблица
   218 и все четыре реальные ответа используют **`cisList`**.

## Почему прежний запрос не давал причины

`/report/info` предназначен для статуса. В § 4.4.13 документации прямо указан
переход к квитанции для подробностей. Его поле `errorReason` описано только
для `reportStatus=REJECTED`; наличие этого поля при `FAILED` не гарантируется.
Повторный прямой GET подтвердил, что четыре поля приходят от самого API:
подробности не были потеряны при разборе ответа в xTrek.

Даже квитанция в этих случаях содержит только общий результат и счётчики.
Нужен связанный документ события `RNMS_GIS_PROCESSED`. Его `details.state=REJECTED`
не следует путать с верхнеуровневым `reportStatus=FAILED`, а код квитанции `1`
— с кодом обработки отдельного КИ `12`.

## Ограничения и запасной способ через ЛК

- Методы квитанций работают для Квитирования 2.0. Квитанции периода
  Квитирования 1.0 этим способом недоступны (§ 4.4.18).
- Практически проверены четыре отчёта `utilisation` товарной группы 35.
  Нельзя обещать одинаковый набор событий для других типов и стадий обработки.
- Обрабатывать все квитанции и события: массивы могут содержать больше одного
  результата. Отсутствие `docId`, пустой `results`, HTTP 404 или ошибка доступа
  сами по себе не означают успешной обработки и не разрешают повторную отправку.
- Для `RNMS_GIS_ROUTED` документ содержит КИ с ошибками маршрутизации;
  при успешной маршрутизации `docId` отсутствует. Для результатов нанесения
  документ по спецификации содержит все КИ, включая успешные: нельзя считать
  каждый его элемент ошибкой без анализа `code`.
- `/api/v3/receipts/receipt/search?omsId=...` — документированный POST поиска
  с фильтрами, но в этой проверке не применялся: сохранённых reportId достаточно.
  `/documents/search` относится к ожидающим отправки документам и не заменяет
  получение результатов обработки завершённого отчёта.
- Использовать HTTPS с проверкой сертификата и тайм-аутами; не сохранять
  заголовки авторизации в доказательствах. Истёкший токен не обновлять из
  диагностического скрипта; пользоваться штатным процессом обновления.
- Текст ошибки подтверждает результат обработки в тот момент. Он не доказывает
  текущее состояние карточки НК или пригодность отчёта к повторной отправке.

Если API не даёт квитанцию/документ, сохранить ответ и использовать ЛК СУЗ:
«Документы» → «Обработанные документы» → нужный отчёт → меню с тремя точками
→ «Скачать квитанцию» (JSON). Для результата по каждому КМ открыть карточку
отчёта → «Список событий» → «Подробнее». Такой маршрут описан в
[официальной инструкции Честного знака](https://markirovka.ru/knowledge/tovarnye-gruppy/pivo-pivniye-napitki/poluchenie-kvitantsii-po-zakazu-v-stantsii-upravleniya-zakazami).
Пользователь ранее получил в ЛК ту же ошибку 12; настоящая проверка независимо
подтвердила её через API для всех КИ. Интерфейс ЛК в этой задаче не открывался.
