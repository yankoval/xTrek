Параллельные обработчики xTrek

Условия запуска

Все потребители одной очереди работают на одном полном коммите main, с одинаковыми
бизнес-настройками и единым operation_state_path. Пример:
operation_state_path = s3://<отдельный-приватный-бакет>/operations/v1
XTREK_PARALLEL_REQUIRED=1 в окружении службы.
Бакет состояния не подключается к бизнес-триггерам Cloud Functions.
Без operation_state_path сохраняется последовательный режим старых CLI.
Не смешивать старый и новый выпуски при включённой координации.

Для каждого узла: concurrency=1, prefetch=1, уникальное имя worker, позднее
подтверждение сообщений и повторная доставка при потере дочернего процесса.
ETA-задачи ограничены десятью на worker. VisibilityTimeout рабочей очереди
сохраняется: координация защищает также от повторов после его истечения.
Секреты находятся вне выпуска, доступны только служебному пользователю.
Обновление кода вручную; автоматическое обновление не устанавливается.

Состояние операции

Ключ: тип операции + производственный ID/orderId/полный ключ события.
Хеш включает канонический JSON входа и влияющие на результат аргументы.
Повтор с изменённым входом останавливается как OperationConflict.
Все изменения используют IfNoneMatch/IfMatch и ETag. Удаления блокировок нет.

held       — владелец выполняет подготовку, изменяющий запрос ещё не разрешён;
ready      — известная безопасная ошибка, следующий процесс может повторить;
external   — разрешение записано перед изменяющим запросом, результат неизвестен;
uncertain  — запрос завершился неоднозначно, повторная отправка запрещена;
accepted   — подтверждённый ответ сохранён, можно восстановить выходной файл;
complete   — результат завершён, при дубле используется сохранённое значение.

held не передаётся чужому хосту по возрасту. На том же хосте автоматическое
восстановление возможно только после проверки boot/PID/starttime/namespace.
external младше 120 секунд с живым/неизвестным владельцем считается занятой
операцией. Это время ожидания дубля, а не срок выдачи права на второй запрос.
uncertain и старая external требуют сверки. Принятый ответ можно повторно
сохранить без нового API; аналогичное повторение исходного POST запрещено.
При HTTP 429 разрешён повтор после явно полученного отказа по лимиту.
Сетевые ошибки и 5xx не считаются доказательством отсутствия принятого документа.

Защищённые границы

19 logic_* маршрутов: полный ключ события, завершение после всех их этапов.
Подготовка: нормализация, состав SET, эмиссия, нанесение, ввод, агрегация,
отчёты оборудования/наборов, задания печати.
Изменяющие запросы: отдельное выделение SSCC; эмиссия; нанесение;
ввод; агрегация; агрегация наборов; расформирование; переагрегация;
изменение сведений о КИ; потребляющее получение кодов СУЗ.
Сохранённые квитанции проверяются до подписи и запроса.
JSON/CSV/VDF публикуются неизменяемо. Совпадающий результат используется снова,
отличающийся результат останавливает операцию; Downloaded не сбрасывается.
REJECTED сохраняется в техническом состоянии и прекращает автоматические повторы.
EXHAUSTED без локальных кодов восстанавливается через существующие блоки СУЗ;
неизвестная схема/дубли/неполное количество требуют сверки, новый заказ не создаётся.
Старые documentSubmissionLocks без квитанции не игнорируются новым выпуском.

Выпуск

1. Выполнить тесты и независимое испытание на отдельной очереди/бакете,
   с синтетическими СУЗ/True API/SSCC и запретом настоящих HTTP-запросов.
2. Слить проверенный PR, зафиксировать коммит main и архив всего выпуска.
3. Подготовить исходники на всех узлах, сверить SHA256 каждого файла,
   эффективные настройки, сертификаты и зависимости; потребитель нового узла выключен.
4. Штатно остановить текущий worker через SIGTERM и дождаться завершения
   задачи. Не заменять исходники под работающим процессом.
5. Сохранить выпуск/настройки/юниты для отката. Проверить незавершённые
   старые отправки без квитанций: processing/error/finished требуют отдельной
   сверки и записи uncertain перед допуском к новой очереди.
6. Подключить общее состояние, переключить целиком main и запустить первый
   узел. После проверки подписи/источников/ошибок допустить второй.
7. Старую прерываемую VM держать изолированной, пока она не обновлена.
   Перед допуском отключить старый Celery и старого мастера токенов,
   установить тот же main/настройки и выполнить технические проверки.
8. Проверить реальные задания и отсутствие дополнительных отправок.
   Возврат к выпуску без координации допустим только после остановки всех
   потребителей, разбора неоднозначных операций и возврата к одному узлу.

Регламент восстановления

Не удалять объекты состояния, не менять их вручную и не повторять документ
из uncertain. Не публиковать новый исходный UUID ради обхода блокировки.
Сначала зафиксировать состояние, вход, известные квитанции и журнал API.
По productionOrderId/orderId/ИНН/GTIN/типу документа выполнить независимую
проверку в СУЗ/True API. Обнаруженный документ используется, не отправляется снова.

Для held: установить доступ к точному хосту владельца и подтвердить гибель
его процесса. На нём выполнить:
python -m xtrek.operation_admin prove-dead --owner-file <owner.json>
Сохранить вывод приватно как proof.json. Доказательство годно 120 секунд.
На любом доверенном администрируемом узле выполнить:
python -m xtrek.operation_admin recover --state-path <s3://.../операция/хеш.json> \
    --proof-file <proof.json>
Изменение held -> ready проходит CAS; новый владелец получает право подготовки.

Для external/uncertain передать также --verified-result-file <result.json>:
эмиссия — квитанция с orderId, expectedCompleteTimestamp, omsId, productionOrderId;
нанесение — квитанция с reportId и связями исходного задания;
документ True API — квитанция с document_id и связями задания;
коды — orderId и полный подтверждённый список codes;
SSCC — подтверждённое назначение palletNumbers и параметров паллет.
Администратор обязан проверить содержание результата независимо. CLI проверяет
владельца/свежесть доказательства/CAS, но не подтверждает результат в API.
После accepted штатное повторное выполнение того же этапа сохраняет квитанцию
без нового запроса. CLI сам бизнес-API и маршрут не запускает.
Если API не позволяет установить результат или хост владельца недоступен,
операция остаётся остановленной до ручной сверки/доказанной изоляции владельца.

Мастер токенов

Потребители читают tokens-v2.json, tokens_read_only=true. Работающий мастер
всегда один. Резервный таймер выключен. Перед переключением остановить таймер
и дождаться завершения старого oneshot; убедиться, что его общая блокировка
released. При аварии с held нужны доказательства остановки владельца и отдельная
контролируемая процедура. Не включать резервный мастер только по возрасту lock.
После переключения проверить все шесть scopes и действующие форматы токенов.
