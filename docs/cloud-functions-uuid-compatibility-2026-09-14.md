# Проверка xTrek UUID и облачных функций перед пунктом 6

Дата: 14.09.2026. **Прямой несовместимости миграции UUID с проверенными контрактами cf не обнаружено.**
Обязательного изменения форматов событий, подписи, заданий или облачной авторизации
для перехода True API JWT → UUID не выявлено. Это вывод по коду, локальным контрактным
тестам и действующим настройкам маршрутизации, а не утверждение о побайтовой
идентичности локального cf и всех развёрнутых функций.

## Объём и происхождение

- xTrek: текущая ветка `feature/token-purpose-model`, после успешного пилота пункта 5.
- cf: `57612b1551ff2f4d3bd79e500a111704cb363cc1`, ветка
  `fix/prnsrv-ephemeral-policy-principal`. Существующие ahead-коммит и изменение
  `.gitignore` сохранены; исходный checkout не редактировался.
- Прочитаны метаданные **13 активных версий** функций и **21 триггера** Yandex Cloud.
  Значения секретных переменных не сохранялись в отчёт.
- Проверены все пять компонентов cf и интерфейс xTrek → SSCC. Прочие найденные
  функции, включая `scanserver-api`, `bukupl`, `bot`, `backupcsv`, — на уровне
  инвентаризации метаданных/подключённых триггеров, без заявления о полном аудите их кода.
- Продуктивные функции в ходе этой проверки не вызывались. Сообщения в рабочие
  очереди и MAX не отправлялись. Службы, триггеры, функции и токены не менялись.

Метод [GetVersionByTag](https://yandex.cloud/en/docs/functions/functions/api-ref/Function/getVersionByTag)
возвращает конфигурацию версии, но не исходный ZIP. Контрольные суммы исходников
развёрнутых версий не сверены; сохранены идентификаторы `$latest`, runtime и
безопасная часть настроек. Успешный production-пилот пункта 5 отдельно подтверждает
работу фактической цепочки подписи для attached challenge и detached ping.

## Матрица совместимости

| Компонент | Контракт с xTrek | Вывод для UUID |
|---|---|---|
| `bucket-to-queue-message-trigger` | Celery v2: Base64 JSON `[args, kwargs, embed]`, `tasks.process_s3_event`, аргумент `{bucket,key}` | Совместим. Токены не передаются в сообщении; проверены 10 маршрутов реального xTrek-router. |
| `ymq-sig` / облачная `sign` | Из сообщения извлекает bucket/key; подписанные GET/PUT-ссылки, результат `key + ".sig"` | Совместим. Содержимое challenge и формат итогового токена не интерпретирует. Проверены 3 формата входного сообщения для `.txt` и `.json`. |
| `sign-trigger-to-que-function` и SignJS | Триггеры `sign/*.txt` и `sign/*.json`; SignJS возвращает `.sig` | Обе нужные конфигурации активны. На `.sig` они повторно не срабатывают; поддержка подтверждена также пилотом. Исходника этой отдельной функции в cf нет. |
| `task-agg-worker` | Задание оборудования → то же JSON + `task-export-signed-link` | Поля задания сохранены. Реестр CRPT не читает. Есть отдельное несоответствие настроек отключённого триггера, см. ниже. |
| `prnsrv-generator` | Производственное задание → CSV/VDF; SSCC через собственный пакет `prnsrv` | От формата CRPT-токена не зависит. В сборке закреплён `prnsrv@698600cd571f5f9adf8b21e86f6582e210d9b3ce`; тесты прошли именно с этой версией. Зависимости от пакета xTrek нет. |
| `max-messenger-notifier` | Читает отчёты оборудования и связанные задания, использует MAX_BOT_TOKEN | Независимая авторизация, неизменённый контракт отчётов; локальные тесты прошли. Уведомления не отправлялись. |
| xTrek → `sscc-generator` | Короткоживущий Yandex IAM Bearer, ограничения адресата и обновление из metadata | Этот токен нельзя заменять UUID CRPT. Интерфейс миграцией не изменён; 7 тестов прошли. |

Ни один из пяти компонентов cf не читает legacy `tokens.json`, `uuidToken` или
серверный `expireDate` True API. Их API keys, IAM/STS credentials, токены MAX и
подписанные S3 URL имеют самостоятельное назначение и не включаются в реестр CRPT.

Активные фильтры S3 не совпадают с `tokens-v2.json`,
`token-pilots/<run>/registry-v2.json` и `tokens.json.master.lock`.
Сам xTrek-router тоже пропускает эти ключи. При выборе другого пути реестра в
пункте 6 нужно сохранить это свойство: не помещать реестр под бизнес-префиксы.
В `sign` переменная `UPLOAD_BUCKET` не задана — согласно локальному коду подпись
возвращается в исходный бакет, как ожидает новый генератор.

## Обнаруженные существующие дефекты cf

### 1. Ошибка отправки в очередь скрывается от вызывающей стороны

`bucket-to-queue-message-trigger/index.py:112–125`: исключение `send_message`
логируется, но функция всё равно возвращает `statusCode: 200` и `Processed 0 messages`.
Воспроизведено локально с отказом SQS. Это риск потери событий при ошибках доставки,
независимый от JWT/UUID.

Рекомендуемая правка: явно сигнализировать неуспех обработки при отказе отправки,
с проверкой повторной доставки и идемпотентности для уже отправленных частей batch.
Одного увеличения настроек повторов без изменения обработки исключения недостаточно.

### 2. API-ключ шлюза подписи попадает в журнал в локальном коде

`ymq-sig/index.js:93`: `console.log("Event received:", JSON.stringify(event))`
печатает заголовки, включая `X-Api-Key`. Локальный тест с синтетическим ключом
подтвердил его присутствие в журнале. Реальные журналы/ключи не извлекались;
побайтовое совпадение облачной версии с этим файлом не подтверждено.

Рекомендуемая правка: убрать полный event из журналирования, оставив action,
request ID и безопасные метаданные без заголовков, тела и presigned URL.

### 3. Префикс отключённого триггера агрегации не совпадает с фильтром кода

Облачная `task-agg-worker` настроена на `FILTER_PREFIX=T-GB`, а триггер
`uploaded-xtrek-equpment-task` — на `upAggXtrakTasks/` и сейчас **PAUSED**.
Локальный обработчик проверяет полный `object_id.startswith(filter_prefix)`:
`upAggXtrakTasks/T-GB-1.json` пропускается. Воспроизведено локально.

Это не причина текущего сбоя UUID и не доказательство сбоя действующей агрегации:
триггер отключён. Перед его возможным включением нужно согласовать полный префикс
или правило фильтрации имени файла и проверить исходник развёрнутой версии.

## Прогоны

- **57 тестов и 10 вложенных проверок:** prnsrv-generator — 23,
  max-messenger-notifier — 24, bucket-to-queue — 3, xTrek SSCC IAM — 7.
- **30 проверок контрактов:** 24 Python и 6 Node.js.
- В тестах Python реальные socket-соединения блокировались до сбора тестов.
  В Node.js SDK-клиенты заменены контролируемыми заглушками внутри VM.
- Тесты cf выполнялись из копии в `/tmp`. Воспроизводящие существующие дефекты
  проверки сохранены как диагностические результаты `findings`, не выданы за
  доказательство их исправления.

Контрактные проверки из корня xTrek:

```sh
python tools/check_cf_token_contracts.py --cf-root /path/to/cf \
  --triggers reports/cloud-compatibility-2026-09-14/triggers.json \
  --output reports/cloud-compatibility-2026-09-14/contracts.json
node tools/check_cf_sign_contract.cjs /path/to/cf/ymq-sig/index.js \
  reports/cloud-compatibility-2026-09-14/contracts.json \
  reports/cloud-compatibility-2026-09-14/sign-contracts.json
```

Для тестов отдельной скопированной функции: `python tools/run_cf_unit_checks.py
/path/to/copy <test-path>`. Для prnsrv-generator переменная `CF_PRNSRV_SOURCE`
должна указывать на checkout закреплённого коммита prnsrv. Тестовые зависимости:
pytest, зависимости функций, moto[sqs], Pillow, python-barcode.

Сводка (локальный артефакт `../reports/cloud-compatibility-2026-09-14/summary.json`),
версии без секретов (локальный артефакт `../reports/cloud-compatibility-2026-09-14/versions-redacted.json`),
триггеры (локальный артефакт `../reports/cloud-compatibility-2026-09-14/triggers.json`),
контракты Python (локальный артефакт `../reports/cloud-compatibility-2026-09-14/contracts.json`),
контракты подписи (локальный артефакт `../reports/cloud-compatibility-2026-09-14/sign-contracts.json`),

## Перед пунктом 6

Изменять форматы обмена с cf ради UUID не требуется по проверенным контрактам.
Рабочее переключение пока не выполнено. В его план следует включить сохранение
раздельных авторизаций, безопасного пути реестра и текущих рабочих триггеров.
Два дефекта доставки/журналирования стоит исправить отдельной проверяемой правкой cf;
выдавать их за исправленные результатом этого аудита нельзя.
