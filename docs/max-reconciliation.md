# MAX: общая сверка и отложенные проверки

Паллетный отправитель и отправитель ссылок на задания применяют каждую полученную
страницу истории ко всем неподтверждённым записям своего реестра и чата. Совпадения
сохраняются сразу: ошибка следующей страницы не отменяет подтверждения. Для
записей с MID используются пакеты до 100 идентификаторов вместо чтения истории.
Отсутствие MID в ответе не разрешает повторный POST.

Сверка также проверяет новые полученные сообщения на конфликт с уже подтверждёнными
записями. Разные MID для одной доставки фиксируются в `pallet_history_conflicts`;
конфликты ссылок — в `task_history_conflicts`. Доставка переходит в неопределённое
состояние, прежний MID сохраняется. Флаг конфликта блокирует быстрый возврат успеха,
новый POST и автоматическое подтверждение, в том числе после перезапуска. Повтор
того же MID на пересекающихся страницах конфликтом не является. Для снятия флага
нужна отдельная ручная сверка; обычный GET его не снимает.

Паллетный реестр сохраняет исходную подпись и идентификатор бота в новой таблице
`pallet_delivery_proofs`. Таблица `deliveries` и её ключи не меняются. Старые записи
без подписи подтверждаются по точному имени вложения либо по сохранённому MID,
боту, чату, отчёту, SSCC и наличию изображения. Старую неизвестную подпись нельзя
заменять подписью нового рендера. Изменённая идентичность исходника блокируется.
Повтор до POST использует сохранённую подпись, даже если новая версия формирует
другой текст: отправленное содержимое и доказательство для GET остаются одинаковыми.
Подтверждённые записи проверяются до MAX-запросов; изменение рендера не приводит
к повторной доставке того же исходника.

HTTP 429, 5xx и транспортные ошибки GET откладывают проверку. Отдельное расписание
используется для успешных GET, пока ожидаемое сообщение отсутствует. Начальная
задержка — 5 секунд, далее удвоение до 300 секунд со случайной прибавкой до 20%
внутри этого предела. `Retry-After` (секунды или HTTP-дата), если он больше,
имеет приоритет над пределом. Сроки и счётчики сохраняются в SQLite в таблице
`max_retry_schedule`. Повторное обращение до срока не увеличивает счётчик.
Найденное в общей истории сообщение подтверждается независимо от его срока.

Для общей HTTP-паузы двух процессов при будущем выпуске укажите один и тот же
доступный им SQLite-файл:

- в JSON конфигурации паллет: `max_retry_state_path`;
- в окружении отправителя ссылок: `XTREK_MAX_RETRY_STATE_PATH`.

Родительский каталог должен уже существовать. Без настройки каждый отправитель
сохраняет HTTP-паузу в своём реестре. Это общий cooldown, а не ограничитель числа
запросов в секунду. Конфигурация промышленного сервера этим изменением не меняется.

Celery повторяет только явно отложенную работу (`MaxRetryLater`), используя
сохранённый срок. Новый вызов сверяется с реестром: `POST_STARTED`,
`POST_UNCERTAIN`, `POSTED_UNCONFIRMED` не разрешают новый POST. Известный MID
сохраняется до подтверждающего GET. Ошибки валидации не получают бесконечный retry.
Старые задания без записи доставки автоматически не переопубликуются.

Полный полученный проход истории переиспользуется внутри экземпляра отправителя
до 30 секунд. Кэш не является постоянным общим индексом двух процессов: после
перезапуска история может читаться заново. Подтверждения и задержки при этом
сохраняются. Граница истории и прежняя явно разрешённая политика ограниченного
прохода не расширяются. Неполная история не разрешает повтор неопределённого POST.
Паллетная доставка сериализуется файловой блокировкой рядом с реестром на VPS;
импорт модуля рендеринга на Windows не требует `fcntl`.

Миграция добавляет только вспомогательные таблицы при открытии существующего
реестра; новый паллетный реестр по-прежнему требует явной инициализации. Перед
будущим выпуском нужны резервные копии реестров и настроек, завершение текущей
работы и полный выпуск из `main`. Новые worker/poller/notifier не требуются.
Откат исходников не удаляет MID и подтверждения; вспомогательные таблицы можно
оставить. Старый код не использует расписание задержек и отдельные флаги конфликтов;
при откате требуется учитывать сохранённые конфликты и не снимать блокировку повторной отправки.

Все проверки выполняются без MAX/S3/RabbitMQ: подменены HTTP, хранилище и публикация
повторной задачи. Регрессии покрывают пакетные частичные ответы, несколько доставок
на одной странице, 429 на следующей странице и после POST, перезапуск, сохранение
MID, две конкурентные доставки, неоднозначные совпадения и совместимость старого
реестра. Для тестов рендеринга дополнительно нужны `python-barcode` и `zxing-cpp`.
