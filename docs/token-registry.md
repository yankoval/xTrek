# Модель токенов по назначению

`xtrek.token_registry` реализует пункт 2 миграции: явную идентичность токенов, проверку метаданных, выбор, преобразование старых записей и локальное приватное хранилище. Модуль не обращается к сети, не ищет конфигурацию, не подписывает данные и не обновляет токены самостоятельно.

## Поля и идентичность

`TokenRecord` — неизменяемая запись:

| Поле | Правило |
|---|---|
| `purpose` | `true_api` или `suz`, всегда явно |
| `environment` | `production` или `sandbox`, всегда явно |
| `inn` | Строка из 10/12 цифр; принадлежность организации задаёт вызывающая сторона |
| `format` | `JWT` или `UUID`; формат не определяет назначение |
| `token` | Секретная строка, исключена из repr |
| `expireDate` | Обязательное время с зоной, исходное представление сохраняется |
| `expiry_source` | `server` для UUID True API; `jwt_exp` для JWT; для СУЗ UUID — `server` либо явно рассчитанное `suz_ttl` |
| `issuer_base_url` | True API v3/v4 выбранного контура, где выдаётся соответствующий токен |
| `connection_id`, `oms_id` | Обязательные UUID для СУЗ, запрещены для True API |
| `auth_uuid`, `certificate_sha256` | Необязательные публичные метаданные выдачи; не заменяют идентификаторы подключения |

Логическая идентичность: `(environment, purpose, inn, connection_id, oms_id)`. Ключ хранения дополнен `format`, чтобы при миграции сохранить JWT для явно выбранного возврата. Идентификаторы подключения нормализуются в нижний регистр. Значение токена остаётся непрозрачным секретом.

JWT payload декодируется только для проверки метаданных: `expireDate` должен точно соответствовать `exp`, а `inn`, если присутствует в JWT, — выбранной организации. Это не проверка подписи JWT. Источник данных должен быть доверенным; модель сама не доказывает полномочия владельца.

## Использование

```python
from xtrek.token_registry import TokenRegistry

registry = TokenRegistry.load(private_path)
record = registry.select(
    purpose="true_api", environment="production", inn=organization_inn,
    preferred_format="UUID",
)
if record is None:
    raise RuntimeError("Нет действующего UUID True API")
remaining = record.remaining_seconds()
# record.token передаётся клиенту; record/to_dict не выводить в журнал.
```

СУЗ выбирается с `purpose="suz"` и обоими идентификаторами. Ни один из них нельзя пропускать ради поиска первого UUID. При наличии только одного активного формата True API можно не задавать `preferred_format`. При одновременном наличии активных JWT и UUID без политики — ошибка. Явно запрошенный истёкший/отсутствующий формат возвращает None, без скрытого перехода на другой.

Выбор возвращает одну запись, поэтому секрет и оставшийся TTL всегда относятся к одному токену. На точной границе expireDate запись уже неактивна. Истёкшие записи допустимы в хранилище для диагностики, но не выбираются.

`registry.upsert(record)` заменяет только запись с тем же ключом хранения. Изменения другого контура, назначения, ИНН, СУЗ-подключения или формата сохраняются. Дубликаты ключа во входном файле отклоняются: порядок массива не должен определять результат. Метод upsert — явное изменение вызывающей стороны; координация нескольких писателей и сетевой CAS в этот модуль не входят.

## Хранение и совместимость

Версия файла отделена от старого массива `tokens.json`:

```json
{"schema_version": 2, "tokens": []}
```

`save(path)` пишет snapshot через временный файл и atomic replace, с fsync содержимого и правами 0600. Родительский приватный каталог заранее создаёт вызывающая сторона. Ссылка вместо целевого файла отклоняется. Метод не обеспечивает межпроцессную блокировку и не объединяет параллельные записи; мастер и CLI используют общую S3-блокировку на время выдачи и публикации. `to_dict` содержит секреты и предназначен только для приватной сериализации.

В пункте 3 генератор, мастер и потребители подключены к модели через `TokenProcessor` и `PurposeTokenAccess`. Использование нового файла включается явно через `tokens_registry_path`; без него читается исторический массив. Production переведён на v2; с 16.09.2026 все три действующие организации используют UUID True API. См. [итог переключения](uuid-rollout-complete-2026-09-16.md). Новый реестр запрещено размещать по прежнему `tokens_path` или по ключу с именем `tokens.json`.

## Преобразование legacy

`migrate_legacy_record` принимает назначение, контур, ИНН и issuer явно. Вызывающая сторона предварительно подтверждает происхождение записи. Функция не угадывает назначение по форме секрета и не создаёт новый срок «сейчас +10 часов».

- JWT: срок только из `exp`, старое `ДействуетДо` не продлевает его.
- Auth/СУЗ: необходимы явно выбранные connection_id/oms_id; legacy `Идентификатор` должен совпасть. Для срока без зоны явно передаётся `legacy_timezone`, например `Europe/Moscow` для подтверждённой исторической схемы.
- UUID True API: нужен оригинальный серверный `expireDate`; одного legacy `ДействуетДо` недостаточно.
- Сам импорт старого массива через `TokenRegistry.load/from_dict` запрещён. Массовая конвертация рабочих данных в этом этапе не выполняется.

## Подключение генератора, мастера и потребителей (пункт 3)

Все компоненты используют `load_config()` и итоговый `TOKENS_CONFIG`. Настройки подписи,
ранее передававшиеся генератору отдельно через переменную `token_config`, нужно перенести
в эту общую конфигурацию. Мастер передаёт генератору тот же словарь настроек.

Пример дополнения конфигурации для последующего согласованного переключения:

```json
{
  "tokens_path": "s3://your-bucket-name/tokens.json",
  "tokens_registry_path": "s3://your-bucket-name/tokens-v2.json",
  "tokens_environment": "production",
  "true_api_token_format": "JWT",
  "true_api_token_formats": {"1234567890": "UUID"},
  "tokens_allowed_inns": ["1234567890"],
  "suz_ping_sign": true
}
```

ИНН в примере синтетический. `tokens_allowed_inns` ограничивает **мастер**;
политика `true_api_token_formats` задаёт формат True API по ИНН у всех читателей.
Для СУЗ всегда выбирается назначение `suz`, connection_id и OMS из карточки организации.
Явно переданный OMS дополнительно сверяется с карточкой. Клиент не перевыпускает токен:
при отказе авторизации его callback перечитывает S3 и выбирает прежнее назначение и область.
Основные производственные сценарии запрашивают `production`; они отклонят реестр,
настроенный на sandbox. NK CLI передаёт контур из `--sandbox` явно.

```python
token = processor.get_token_value_for(inn, purpose="true_api")
suz_token = processor.get_token_value_for(
    inn, purpose="suz", conid=connection_id, oms_id=oms_id,
)
```

Генератор `issue_token` возвращает `TokenRecord` только после проверки:

- True API UUID: `unitedToken=true`, значение только из `uuidToken`, срок только
  из `expireDate`. JWT берётся из `token`, срок — из `exp`.
- СУЗ: отдельный `simpleSignIn/{connection_id}`, `token`; при отсутствии серверного
  срока применяется документированный TTL 10 часов от начала запроса выдачи.
- Подпись challenge: точные данные в `{inn}_{uuid}_dataToSign.txt`; SignJS возвращает
  attached CAdES в `.sig`. Промежуточные объекты удаляются и при ошибке.
- СУЗ проверяется `GET /api/v3/ping?omsId=...` с `clientToken`, совпадением OMS и
  непустыми версиями. При `suz_ping_sign=true` точный путь с query подписывается
  через `.json` (detached CAdES), подпись передаётся в `X-Signature`.
- True API проверяется `GET /elk/product-groups/balance/all` с Bearer-токеном.
  Этот UUID не передаётся в СУЗ ping.
- TLS проверяется, редиректы запрещены, HTTP timeout — 10 секунд соединение /
  30 секунд чтение. Только проверочный GET повторяется до трёх попыток при
  транспортных ошибках, HTTP 429 и 5xx. Запрос выдачи не повторяется.

Мастер обновляет только отсутствующие/истекающие записи выбранного формата,
сохраняет остальные назначения/организации и проверяет результат сохранения.
Клиентам запись запрещена. Запись в legacy сохраняет точный срок; True API UUID
в старый массив записать нельзя. Секреты и тела ответов не выводятся в новые журналы.

Мастер и `crpt-auth` удерживают блокировку S3 от чтения до конца цикла:
`tokens_master_lock_path`, по умолчанию `tokens_path + ".master.lock"`.
Захват выполняется через условный PutObject (`If-None-Match: *`). При аварийном
завершении блокировка остаётся; удалять её можно лишь после проверки отсутствия
работающего мастера. Низкоуровневый `save_record` требует координации вызывающей стороны.
Старые версии мастера эту блокировку не используют — одновременно их запускать нельзя.

При первом переключении нужно заранее подготовить отдельный объект schema v2
через явную миграцию проверенных старых записей. Отсутствующий/недоступный S3-источник
останавливает выдачу: мастер не создаёт поверх него пустой реестр. Перед переключением
читателей обеспечить для них полный комплект токенов; после переключения старый файл
больше не обновляется новым мастером. Локальный кэш нового формата — `~/tokens-v2.json`, 0600.

Ошибка проверки или публикации завершает цикл с ошибкой. Для СУЗ предыдущий токен
мог уже потерять силу после выдачи нового; откат старого файла не восстанавливает
его действительность. Это требует проверки причины сбоя перед следующим запуском.
JWT, сохранённый рядом с UUID, также может истечь: возврат политики на JWT допустим
только при наличии действующего JWT. Автоматического fallback нет.

Проверки: `tests/test_token_purpose_integration.py`, `tests/test_token_worker.py`,
`tests/test_tokens_read_only.py` и регрессионные тесты потребителей. HTTP, подпись и S3
подменяются тестовыми реализациями; production-токены для этих тестов не нужны.
Связанная задача: [проверка токенов после создания, #88](https://github.com/yankoval/xTrek/issues/88).


При выбранном ИНН CLI True API/NK завершает работу, если нужного токена нет,
без подстановки токена из окружения. Для СУЗ выбор по ИНН также не использует
`HONEST_SIGN_TOKEN` из окружения. Проверки отчётов в режиме нового реестра
игнорируют `TRUE_API_TOKEN`. Явно переданный пользователем `--token` остаётся
отдельным ручным способом авторизации там, где он предусмотрен CLI.
Неоднозначный конфигурационный `client_token` больше не используется для
поиска владельца GTIN: этот запрос выбирает `purpose=true_api` из хранилища.
