## Существенное ограничение текущего кода

`tokens_registry_path` выбирает источник **для всего TokenProcessor**, а не для одного ИНН.
`tokens_allowed_inns` ограничивает только обновление мастером. Поэтому конфигурация
«общий v2 + обновлять только Смарткосметик» оставит остальные записи без обновления.

Для текущей реализации нужен единый v2-реестр и один новый мастер для всех трёх
организаций. Формат True API меняется только у Смарткосметик; остальные сохраняют JWT,
СУЗ у всех сохраняет своё отдельное назначение и формат UUID. Операционное изменение
источника реестра при этом затрагивает всех читателей переведённого процесса.

До отключения старого мастера требуется инвентаризация всех потребителей legacy-файла,
включая отдельные CLI, другие серверы и рабочие места. Аудит cf не заменяет эту проверку.
Новый мастер не публикует обновления обратно в legacy; оставить старых читателей
на нём означает получить устаревшие токены. Два независимых мастера, выдающих токены
одного подключения СУЗ, также недопустимы.

Первичная инвентаризация JSON-конфигураций в `~/Scripts` на VPS и в локальных
`Documents/CodexCHETHE`, `python-projects` уже выявила дополнительный реальный источник:
`/Users/ivankiselev/python-projects/xTrek/tokens_config.json` на Mac указывает на тот же
production `tokens.json` без v2. На VPS обнаружен действующий
`/home/ivankiselev1975/Scripts/Testing/tokens_config.json`; остальные найденные пути
с `your-bucket-name` являются примерами, а не подтверждёнными потребителями.
Само наличие конфигурации на Mac не доказывает запущенный процесс, но её нужно
включить в переход, если рабочие CLI продолжают использоваться. Конфигурации из
переменных окружения и другие рабочие места этой файловой проверкой не покрыты.

## Предлагаемая конфигурация

Ниже проект дополнения, **не применённый** к production. Он предполагает завершённую
инвентаризацию и переход всех нужных читателей на v2. Остальные параметры и секреты
берутся из действующей конфигурации, а не из этого документа.

```json
{
  "tokens_path": "s3://20ab2a0c-2726-4ba1-9c7c-7deae82941ff/tokens.json",
  "tokens_registry_path": "s3://20ab2a0c-2726-4ba1-9c7c-7deae82941ff/tokens-v2.json",
  "tokens_master_lock_path": "s3://20ab2a0c-2726-4ba1-9c7c-7deae82941ff/tokens-v2.json.master.lock",
  "tokens_environment": "production",
  "true_api_token_format": "JWT",
  "true_api_token_formats": {"9723161905": "UUID"},
  "tokens_allowed_inns": ["7733154124", "9718180660", "9723161905"],
  "tokens_purposes": ["true_api", "suz"],
  "tokens_refresh_before_expiry_seconds": 1800,
  "tokens_read_only": true,
  "suz_ping_sign": true
}
```

Мастер явно создаёт TokenProcessor с правом записи. Клиенты остаются read-only.
Перед публикацией проверить отсутствие занятого ключа реестра/блокировки;
не перезаписывать неизвестный существующий объект.

## Порядок переключения после закрытия условий

1. Разобрать оставшиеся сообщения sign или подтвердить их изоляцию от новых запросов;
   выполнить свежую безопасную проверку подписи. Не очищать очередь целиком.
2. Завершить инвентаризацию читателей и согласовать общий переход хранилища при UUID
   только для Смарткосметик. Если нужен независимый переход единственного ИНН без
   обновления остальных читателей, сначала реализовать и проверить отдельную схему
   маршрутизации источников; текущая реализация её не поддерживает.
3. Зафиксировать полный проверенный исходный код в релизе, включая untracked-модули.
   Подготовить новый каталог релиза, его конфигурацию и точные изменения units/ссылок,
   сохранив текущие значения для отката. Не накладывать файлы поверх активного релиза.
4. Проверить отсутствие активных бизнес-задач Смарткосметик непосредственно перед
   окном переключения. Сделать свежую резервную копию. Остановить старый мастер
   и дождаться его завершения; согласованно остановить читателей на время смены источника.
5. Явно мигрировать свежие проверенные legacy-записи в отдельный v2-объект с исходными
   сроками, ИНН, OMS и connection_id. Подготовить полный комплект для трёх организаций.
   Выдать и проверить только True API UUID Смарткосметик. Без необходимости не
   перевыпускать СУЗ. Не использовать UUID из пилота 14 сентября: срок уже прошёл.
6. До подключения потребителей проверить выбор записей: UUID Смарткосметик,
   JWT остальных двух организаций, SUZ всех трёх. Выполнить проверки авторизации
   чтением True API и ping СУЗ. Не отправлять бизнес-документы ради проверки.
7. Переключить согласованных читателей и единственный мастер на новый релиз/реестр.
   Проверить загрузку S3, отсутствие ошибок авторизации и работу таймера.
8. Наблюдать штатное обновление и перечитывание нового токена живым потребителем.
   Зафиксировать результат до расширения использования UUID на другие ИНН.

## Откат

При ошибке выбора/авторизации/публикации остановить новый мастер и обработку,
сохранить диагностические метаданные без токенов. Проверить, какие токены действительно
действуют; возврат старого JSON не восстанавливает отозванный токен СУЗ.

Для возврата legacy-потребителей подготовить актуальный legacy-реестр с рабочими JWT
и SUZ, при необходимости выпустив и проверив недостающий JWT. True API UUID в старый
формат не записывать. Не восстанавливать слепо снимок от начала подготовки.
Вернуть прежние релизы/конфигурацию, запустить только один мастер, затем потребителей
после проверки авторизации. Сохранить v2 для расследования, не использовать его как
автоматический неявный fallback.

- Зафиксированный релиз и конкретные изменения сервисов для этого списка.
- Повторные проверки авторизации и отсутствие задач непосредственно перед окном.
