# Обратная связь по окончательным ошибкам отчётов

Уведомление создаётся, когда подтверждён отказ документа, некорректный отчёт,
недопустимое состояние кодов или конфликт, требующий ручной сверки. Неопределённый
результат бизнес-POST остаётся защищённым `ReconciliationRequired` и требует сверки.
Техническая ошибка, отсутствие данных в ещё не согласовавшихся системах, `IN_PROGRESS`
и ожидание готовности SET не являются окончательным отказом. Число попыток не меняет
этот вывод: Celery продолжает повторные проверки с ограниченной задержкой без
терминального события. Завершённые отправки сохраняют отдельные durable guards.

## Явный отказ СУЗ при отправке нанесения

HTTP 400 с `success=false` и единственной известной ошибкой поля останавливает
обработку сразу, без повторной отправки и без запуска следующих стадий:

| Код СУЗ | Поле | Причина и исправление |
| --- | --- | --- |
| 7570 | `attributes.productionDate` | Дата производства вне диапазона `1970-01-01 — 2100-01-01`. Сверить фактическую дату, исправить её в исходном задании, проверить год и формат `YYYY-MM-DD`. |
| 7580 | `attributes.productionDate` | Дата производства позже текущей даты. Сверить и исправить фактическую дату производства; не подставлять сегодняшнюю дату автоматически. |
| 7745 | `attributes.expirationDate` | Срок годности раньше текущей даты. Проверить дату в задании и согласовать исправление. |

Пары код/поле подтверждены промышленными ответами СУЗ. В уведомлении указываются
HTTP 400, код, поле, причина, требуемое исправление и стадия «Отправка отчёта о
нанесении». Повторная отправка после исправления требует отдельного согласования.
Текст строится из фиксированного шаблона, а не из произвольного `fieldError` API.
Send/route guards сохраняют `rejected` и восстанавливают тот же отказ после
перезапуска. Неизвестные коды, другие поля, смешанные ошибки или признаки принятого
документа остаются неопределённым результатом, требующим сверки.

Уже записанные `uncertain` guards и отправленные уведомления не переклассифицируются
и не переотправляются этим выпуском. Исторические документы не запускаются повторно.

## Продолжение после нанесения

`APPLIED`, промежуточные/неизвестные статусы и частично обновившийся `INTRODUCED`
помечаются `waitingstatus`. Подтверждённые `WRITTEN_OFF`, `RETIRED`, `DISAGGREGATED`
остаются недопустимыми для исходного отчёта. Дубли кодов/SSCC и другие ошибки входа
не скрываются ожиданием. Все коды `INTRODUCED` завершают прежнюю проверку.

Для продолжения после `APPLIED` одного статуса недостаточно. `applied_checkpoint`
читает исходный отчёт, точное utilisationTask, receipt, report и send-utilisation guard:
состав кодов, productionOrderId, reportId и fingerprint отправленного задания должны
совпасть. Нужны accepted/complete и SUCCESS. Отсутствующие данные ожидаются;
uncertain/external/rejected или противоречия требуют сверки. Эта ветка не вызывает
нанесение повторно. UNIT продолжает ввод через прежние guards. SET создаёт/находит
виртуальные компоненты и ожидает их готовность; недостающие статусы не завершают
route guard. После готовности используется обычная защищённая отправка агрегации.
Подтверждённый отказ нанесения или ввода компонента даёт терминальное уведомление.

Создатель виртуальных компонентов исторически возвращает None при успехе, включая
результаты старых complete guards. Обёртка отчёта возвращает True после успешного
вызова, чтобы не запускать ошибочный повтор проверки уже нанесённых кодов.

## Содержание и доставка

Каждое новое сообщение содержит артикул (`productionOrder.Article`), партию
(`productionOrder.PasportData.Batch_number`) и полный ID отчёта. Для виртуального
компонента проверяются контракт его ID, GTIN и существующий родительский заказ;
контекст берётся из родителя. Отсутствующее значение отображается как «не указан».
Unicode и слеши сохраняются. Управляющие символы экранируются, длина ограничена,
похожие на КИ/секреты значения скрываются. MAX получает plain text без HTML/Markdown.
Причина и стадия заданы русскими безопасными шаблонами; произвольные тексты API,
исключения, токены и полные КИ в сообщение не включаются.

Маршрутизация неизменна: только точный верхнеуровневый `operator` исходного заказа,
известные значения используют свой маршрут, прочие — явно заданный default.
Первое разрешение сохраняет ID/operator/контекст. Выбранные адресат и тело сообщения
не меняются после привязки. Старые сообщения и неизвестные результаты MAX POST
не переформатируются: это необходимо для точного GET-reconcile.

Общий S3 ledger использует CAS; SQLite поддерживает процессы одного хоста.
SQLite добавляет nullable context_json транзакционно, сохраняя совместимость
старого schema version 1. Существующие строки сохраняются. Создание SQLite ledger
по-прежнему явно выполняется командой init, отсутствующий файл не восстанавливается.
POST_STARTED резервируется до единственной попытки MAX POST и не истекает.
Только точное совпадение текста, чата, бота и message ID через GET даёт CONFIRMED.
Timeout/ошибка/перезапуск не разрешают повторный POST. Operator/default routing,
защищённые ID и persistence-only retry терминальных событий сохраняются.

## Уже записанные ложные события

Выпуск не удаляет события, не сбрасывает guards и не переигрывает историю.
Для каждой затронутой задачи перед отдельным исправлением:

1. Снять свежий снимок исходников/ETag, send/route guards, всех квитанций, S3 outbox,
   active/reserved/scheduled задач и попыток. Установить конкретную причину ожидания.
2. Если check=finished и документы успешны, ничего повторно не публиковать.
3. Для незавершённой задачи доказать SUCCESS нанесения, точный состав и fingerprint,
   состояние компонентов и отсутствие неопределённой отправки следующей стадии.
4. Согласовать точечный план: сохранить прежнее terminal event с историей доставки,
   оформить отдельное аудируемое разрешение продолжить конкретную стадию и условно
   изменить только соответствующий fence. Не стирать POST_STARTED/CONFIRMED,
   не менять business guards и не публиковать массовый replay.
5. После отдельного разрешения выполнить одну точечную доставку штатного события
   ожидания/готовности, сверить отсутствие повторного нанесения и конечный результат.

До согласованного исправления прежний fence сохраняется. Это явно указывается
в отчёте о выпуске, а не скрывается удалением сообщения.

## Проверка и выпуск

Тесты используют синтетические S3/Celery/MAX, в том числе конкурирующие процессы,
потерю ответа CAS/POST, перезапуск, ожидание сверх 200 попыток, переход к готовности,
точные fingerprints и контекст сообщений всех категорий. Рабочие документы и
пробные сообщения в чат не используются как тестовые.

Выпускается полный main после CI. Сохраняются настройки, исходники и снимки ledger;
текущие задачи завершаются до warm restart, проверяются реально загруженные файлы.
Откат возвращает полный прежний выпуск, но никогда не подменяет живой ledger старой
копией: это могло бы стереть резервирование отправки. Автообновление не настраивается.
