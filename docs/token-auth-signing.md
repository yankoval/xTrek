# Подпись auth challenge мастером токенов

`crpt_auth` выбирает способ подписи по ИНН из отдельного раздела
`tokens_signing.by_inn`. Настройки `signing.local_by_inn` относятся к документам
и не включают локальную выдачу токенов. Для существующей конфигурации без
`tokens_signing`, а также для отсутствующего в нём ИНН сохраняется файловый
протокол SignJS. Неизвестный mode или неверная локальная запись завершают выдачу
до запроса challenge; локальная ошибка не переключает маршрут на S3.

Шаблон маршрутов, который нужно заполнить после проверки ключа Фито:

```json
{
  "tokens_signing": {
    "by_inn": {
      "7733154124": {
        "mode": "local",
        "thumbprint": "REPLACE_WITH_VERIFIED_FITO_SHA1",
        "store_location": "current_user",
        "pin_file": "/run/secrets/xtrek-fito-pin"
      },
      "9718180660": {"mode": "storage"},
      "9723161905": {"mode": "storage"}
    }
  }
}
```

Замените `REPLACE_WITH_VERIFIED_FITO_SHA1` полным SHA-1 thumbprint из 40
шестнадцатеричных символов. Это шаблон документации, не рабочая настройка.
`pin_file` необязателен только для контейнера с пустым PIN; передавать PIN в JSON
или аргументах команды нельзя. Файл PIN должен быть доступен только владельцу
(например, 0600). Выбор `current_user`/`local_machine` явный, перехода между
хранилищами нет. Раздел конфигурации из более позднего источника заменяет
предыдущий целиком: перед выпуском сверяйте объединённую конфигурацию.

## Требования к ключам и CRL

Мастер на 94 должен использовать Linux CryptoPro CSP/CAdES и `pycades`, собранный
для его Python. Сертификат и соответствующий закрытый ключ должны быть доступны
служебному пользователю мастера в выбранном `My` store. Одного публичного
сертификата или успешного поиска thumbprint недостаточно: нужно подтвердить
`HasPrivateKey()` и успешную подпись синтетических данных тем же пользователем.
Пользователь подтвердил, что закрытый ключ Фитокосметик доступен пользователю
мастера на 94. Перед выпуском остаётся проверить точный выбранный сертификат,
цепочку/CRL и синтетическую attached подпись в окружении этого пользователя.

В локальной папке «Загрузки» найдены `Лесняк.pfx` и `Смарт.pfx`.
По сообщению пользователя, `Лесняк.pfx` — сертификат сотрудника с доверенностью
для ГлобалБио (`9718180660`). Содержимое обоих PFX этим PR не проверено;
наличие файлов не подтверждает их импорт и доступность пользователю мастера.
Сертификат из `Смарт.pfx` нужно сверить с корпоративным thumbprint ниже.

Для ИНН юридического лица из 10 цифр проверяется отдельный атрибут `INNLE`
(`1.2.643.100.4`, включая OID и русское имя `ИННЮЛ`) с точным значением ИНН.
Личный `INN`, в том числе дополненный нулями, не заменяет `INNLE`. Для ИНН из
12 цифр проверяется атрибут `INN` (`1.2.643.3.131.1.1`). Дублированные и
неоднозначные значения отвергаются; текст внутри CN/O не считается ИНН.

Корпоративный сертификат Смарткосметик —
`718E0C464DDC37F8B76FCCDA7903D49AC77BEA1F`, `INNLE=9723161905`.
Наличие его закрытого ключа у пользователя мастера на 94 пока не подтверждено.
Смарткосметик остаётся на файловом маршруте. Личный сертификат не включать
в локальную настройку этого ИНН. Global `9718180660` также остаётся файловым.

Сертификат сотрудника с МЧД требует отдельной явной политики привязки подписанта
к организации. [Официальная инструкция True API по МЧД](https://docs.crpt.ru/gismt/Инструкция_по_использованию_МЧД_в_Системе_маркировки/)
предусматривает `inn` организации в запросе `/auth/simpleSignIn`.
Текущая локальная проверка для 10-значного ИНН требует корпоративный `INNLE`;
если в сертификате сотрудника его нет, эта проверка отклонит подпись до POST.
Поддержка МЧД в локальном маршруте этим PR не заявляется. Проверку `INNLE`
нельзя просто отключить или заменить личным ИНН сотрудника.

На каждом локальном auth подписании вызывается `Certificate.IsValid().Result`
и требуется положительный результат. Затем используются
`Signer.CheckCertificate=True` и `VerifyCades`; восстановленные attached байты
сравниваются с исходными. Native проверка строит цепочку и проверяет статус
отзыва. На 94 нужны доверенные корни/промежуточные сертификаты, актуальные CRL
для цепочки, правильное время и доступ к необходимым CDP. Недоступный или
просроченный CRL нельзя обходить отключением проверки. Отрицательный результат
означает, что проверка не подтверждена; журнал не объявляет сертификат отозванным
без такого доказательства.

API pycades описан в [документации CryptoPro](https://docs.cryptopro.ru/cades/pycades),
проверка цепочки и CRL через IsValid разъяснена
[технической поддержкой CryptoPro](https://cryptopro.ru/forum2/default.aspx?find=unread&g=posts&t=23891).

## Scopes, проверка и неоднозначный POST СУЗ

Auth challenge `data` подписывается как буквальный UTF-8 текст, без декодирования
Base64, в attached CAdES-BES. True API UUID/JWT и СУЗ используют тот же профиль.
Подпись пути SUZ ping с query string остаётся detached. Маршрут подписи не меняет
политику UUID/JWT, environment, OMS, connection_id или разделение scopes.
Перед возвращением записи выдачи выполняется штатная проверка токена:
True API balance GET или СУЗ ping с проверкой OMS и версий.

Выдача СУЗ требует `master_runtime` и удерживаемый writer lock. `crpt-auth` и
`token_worker` используют общий lock. Прямой вызов `get_new_token(mode='auth')`
вне него завершается до сетевых запросов; для ручной выдачи используйте
штатный `crpt-auth`, который проверяет и публикует запись.

Перед POST СУЗ мастер условной записью создаёт и перечитывает отметку
`<master-lock-path>.suz-<scope-sha256>.json` со статусом `attempted`. Scope
включает environment, ИНН, connection_id и OMS. В отметке сохраняются auth UUID
и время; challenge, подпись, PIN и токен в неё не записываются.
`TokenProcessor.save_record` переводит её в `published` только после успешной
публикации проверенной записи. Следующая выдача возможна после `published`.
Новая выдача в другой scope не снимает предыдущую отметку.

Тайм-аут/5xx/невалидный ответ POST, неуспешная проверка или публикация, аварийное
завершение и потеря ответа на запись отметки сохраняют блокировку. Следующий
запуск таймера, CLI или новый процесс не повторяют POST этого scope.
Блокировка не истекает по времени и не снимается восстановлением writer lock.
S3-права мастера должны позволять GET и условный PUT этих объектов; при ошибке
хранилища выдача прекращается. POST не имеет транспортных повторов, включая
429/5xx; повторяется только проверочный GET.

При `reconciliation_required` сначала сверить реестр S3 и конкретную попытку.
Если в реестре уже есть запись с тем же `auth_uuid`, проверить токен штатным
probe и под writer lock завершить `complete_suz(record)` без новой выдачи.
Если токен/публикация неизвестны, требуется отдельное решение оператора после
сверки СУЗ. Автоматически удалять/сбрасывать отметку или переносить старую
локальную копию реестра в S3 нельзя. PR не добавляет команды автоматического
сброса. При откате на старый код отметить, что он не соблюдает эти fences:
оставить мастер остановленным до сверки, чтобы он не повторил неизвестный POST.

## Диагностика и выпуск

Мастер и CLI выводят тип ошибки и разрешённые `stage`/`reason`, например
`stage=signing_storage reason=timeout`,
`stage=signing_local reason=private_key_missing` или
`stage=issuance reason=reconciliation_required`.
Произвольный текст исключений, тела ответов и секреты не выводятся.
Ошибка подписи до POST не даёт предупреждение об отзыве токена СУЗ.

Выпуск выполняется отдельно после слияния PR и разрешения пользователя:

1. Зафиксировать текущий коммит полного `main`, результаты тестов и manifest
   исходников. Исходная промышленная версия для этого изменения:
   `9d8e4c0981e13d5a8f7044e5033a6eba81137a16`.
2. Сохранить рабочие настройки, реестр, unit/drop-in и возможность отката.
   Дождаться завершения текущей задачи мастера и бизнес-задач затрагиваемого
   процесса перед остановкой/перезапуском. Старые fences сохранять.
3. Под пользователем мастера 94 проверить выбранный сертификат/ИНН, закрытый
   ключ, PIN, цепочку/CRL и синтетическую attached подпись; это не выдача токена.
   Только затем явно добавить auth маршрут Фито. Global и Смарткосметик — storage.
4. Развернуть полный выпуск `main`; сверить фактически загруженные исходники,
   Python/pycades и объединённые настройки. Частичное наложение файлов и запуск
   промышленного мастера из ветки PR не допускаются.
5. Сохранить единственный мастер на 94. Резерв 194 должен оставаться выключенным,
   мастер VM — masked. Общий writer lock, сроки и UUID policy сохраняются.
   Потребители читают реестр, собственную выдачу токенов не запускают.
6. После отдельного разрешения на рабочую выдачу проверить штатное обновление
   всех scopes и публикацию, контролируя `stage`/`reason` и SUZ fences.

PR не меняет production-настройки, службы, токены или активные процессы.
Изолированные тесты выполняются `python tools/run_token_regressions.py`:
реальные соединения запрещены. Native Linux CSP/CRL проверка остаётся отдельной
приёмкой на целевом пользователе, не заменяется эмулятором.
