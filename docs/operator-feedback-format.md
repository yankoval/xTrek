# Сообщения оператору о проблемах отчётов

Обновлено 27.10.2026. Реализация: `terminal_feedback`, а не `task_notifier`
(он отправляет задания) и не связанный бот. Добавлена передача TXT через MAX; адресация, постоянное резервирование POST
и запрет повторной отправки сохраняются. GET-подтверждение проверяет также файл. Это проект изменений,
не развёрнутый выпуск. Внешняя ИИ-модель не подключена.

## Формат

Шесть строк: артикул/партия → проблема, количество и номера → одно действие →
остановка → полный ID отчёта → ссылка на приложенный полный список либо номер
обращения для поддержки, если проблемных коробов не больше 10.
Техническая стадия, HTTP/поля API и полный хеш события находятся в деталях.
Короткий номер обращения — первые 16 символов прежнего event_id, не новый ID.
Полный ID отчёта сохраняется без обрезания. Краткие артикул/партия ограничены
80 символами; управляющие символы экранируются. Лимит всего текста — 3500 символов.

На экран выводятся первые два вида ошибок и первые два номера каждого вида.
Количество остальных номеров и видов ошибок указывается явно. Полный список
не режется и сохраняется в `facts_json` события вместе с SHA256 исходного отчёта.
КИ показываются только в короткой форме AI 01/21, без криптохвоста. Нераспознанный
номер не обрезается до похожего: явно указывается, что он скрыт. Ошибки без
безопасного номера отражаются отдельным количеством; нужна исходная диагностика.

## Явное состояние короба и вложений

Для каждого показанного короба сохраняются и выводятся отдельные счётчики состояний
его текущих вложений из отчёта. Они не описывают старые вложения, уже зарегистрированные
под тем же SSCC. Формулировки различают:

- Короб в обороте, а все 6 текущих вложений ещё не в обороте (эмитированы).
- В коробе уже в обороте 2 из 6 вложений; остальные 4 эмитированы. Состояние самого
  короба указывается отдельно — «в обороте», «не найден» или «не подтверждено».
- Короб и все 6 вложений в обороте, состав совпадает — повторное сканирование.
- Короб и все вложения в обороте, но зарегистрирован другой состав — требуется
  сверка, утверждение о повторном сканировании не применяется.

Списанные, выведенные, нанесённые и неизвестные состояния не заменяются общим
«ещё не в обороте». Неизвестность явно показана. В фактах используется необязательное
поле `contents` у короба: только разрешённые статусы и положительные целые счётчики.
Старые снимки без этого поля остаются читаемыми; уже зафиксированные сообщения
не переформатируются. Числа в коротком тексте и полном списке берутся из одного снимка.

## Матрица правил

«В обороте» означает подтверждённый INTRODUCED. «Готовы» — EMITTED без дублей
и признаков родительского агрегата. NOT_FOUND — явный статус, отсутствие ответа
не считается доказательством. Для повторного сканирования проверяется точное
совпадение состава первого уровня через существующий read-only API ЧЗ.

| SSCC и вложения | Диагноз | Действие/поведение |
| --- | --- | --- |
| SSCC не зарегистрированы; все вложения готовы | Обычный новый отчёт | Штатная обработка; уведомления об ошибке нет |
| Все SSCC и все вложения в обороте, состав совпадает | Повторное сканирование по ошибке | Не сканируйте эти короба повторно |
| Часть коробов и все их вложения в обороте; остальные SSCC явно NOT_FOUND, вложения готовы | Частичное повторное сканирование | Проверьте короба в приложении «ЧЗ Бизнес» и повторно сканируйте только короба не в обороте |
| SSCC короба уже использован, все вложения готовы | Проблема только с паспортом короба | Замените паспорт короба и сканируйте весь паллет заново |
| Повтор SSCC коробов внутри отчёта; вложения готовы и уникальны | Проблема только с SSCC | То же действие с паспортом |
| SSCC и вложения в обороте, зарегистрирован другой состав | Это не подтверждённый повтор | Передайте отчёт ответственному для сверки кодов и состава упаковки |
| Вложения в обороте, SSCC не подтверждён в обороте | Состояния упаковки и вложений различаются | Сверка состава; паспорт автоматически не заменять |
| В одном коробе часть вложений в обороте, часть эмитирована | Смешанное состояние короба | Сверка состава; не предлагать повтор целого короба |
| Часть коробов повторная, в других есть списанные/выведенные коды | Смешанная ошибка | Сверка состава; рекомендация частичного пересканирования не применяется |
| Вложения списаны/выведены/расформированы либо дублируются | Ошибка вложений | Указать конкретные КИ и состояние/дубли, передать на сверку |
| Конфликт SSCC паллеты | Ошибка паллеты | Указать SSCC паллеты; правило замены паспорта короба не применять |
| Не хватает статусов или состава для диагноза повтора, API недоступен | Проверка не завершена | Ожидание и штатная повторная проверка, не новый окончательный отказ |
| APPLIED/промежуточные состояния | Возможен штатный прогресс | Прежняя проверка durable checkpoint; не считать повтором по одному статусу |
| У этого же отчёта есть документы/запись отправки нанесения | Возможен собственный прогресс отчёта | Сохранить прежний guarded-маршрут, не объявлять ошибочное сканирование |

Отсутствующий, пустой или неизвестный статус SSCC оставляет диагноз `pending`,
даже если статусы всех вложений получены. Такой ответ сам по себе не создаёт
терминальное событие: после восстановления ответа ЧЗ отчёт проверяется заново.
Короб с эмитированными вложениями признаётся готовым для частичного
пересканирования только при подтверждённом `NOT_FOUND` у SSCC и отсутствии
`parent` у всех вложений. Указанный родительский агрегат требует сверки состава.

При явном конфликте входа применяется прежняя бизнес-классификация. Уведомление
не разрешает автоматическую повторную отправку документов и не меняет статусы.
Для паллет v2 полный повтор требует совпадения состава и статуса самой паллеты.
При частичном повторе паллеты, если они присутствуют, должны быть явно NOT_FOUND;
другие сочетания направляются на сверку. Номер короба — его позиция в развёрнутом
списке отчёта (1-based, включая v2), не произвольный порядковый номер на линии.

## Снимок фактов и совместимость

`AggregationAnalyzer` возвращает прежний словарь ошибок с дополнительным
in-process атрибутом `feedback_facts`. Он содержит только разрешённые поля,
счётчики, безопасные номера, состояния из белого списка и SHA256 источника.
Чужие ответы API, тексты исключений, токены и подписи в него не попадают.
Снимок проходит проверку схемы на записи; несовместимые данные дают общий шаблон.

Факты передаются через TerminalBusinessError и persistence-only retry: при сбое
записи терминального события повторяется запись, а не бизнес-маршрут. SQLite
транзакционно добавляет nullable `facts_json` и `attachment_json`; S3 использует прежний CAS. Первое
событие, привязанный контекст, адресат, текст и вложение остаются неизменными. Уже отправленные
и POST_STARTED сообщения не переформатируются и не переотправляются. Старые события
без фактов получают общий шаблон только если их тело ещё не было зафиксировано.

Новые проверки повтора читают существующие utilisationTask/receipt/report и
send-utilisation guard. Неизвестность/ошибка чтения не считается отсутствием.
Запрос состава выполняется только при наличии INTRODUCED, пачками до 1000 SSCC.
В строгом precheck новый предполагаемый повтор не получает преждевременный
`check=finished`: сначала диагноз сохраняется в outbox либо ожидает подтверждения.
Для собственного прогресса отчёта прежний финальный путь сохраняется.

## Получение полного списка

Если проблемных коробов **больше 10**, формируется TXT в UTF-8 и прикладывается
к тому же сообщению MAX. В коротком тексте указаны количество коробов и наличие
полного списка в файле. При 10 коробах и меньше автоматического файла нет.
Порог считается по уникальным позициям коробов в отчёте, а не числу ошибок:
несколько ошибок одного короба считаются один раз, одинаковые SSCC в разных
позициях — отдельными коробами. Готовые короба `readybox` не входят в список.
Короба с ошибками отдельных вложений также включаются через `problem_boxes`.

Файл содержит полный ID отчёта, все безопасные номера и причины из снимка фактов,
а также полный список проблемных коробов с состояниями короба и текущих вложений.
Криптохвосты в файл не включаются. Имя, текст, размер и SHA256 файла сохраняются
в `attachment_json` одновременно с телом сообщения. Уже привязанные старые события
сохраняют прежний текст без добавления файла задним числом.

Транспорт получает URL через `POST /uploads?type=file`, загружает TXT как multipart
и передаёт токен вложения в единственном `POST /messages` вместе с текстом.
Используются только HTTPS-адреса MAX/oneme без перенаправлений; токен бота не
передаётся файловому серверу. Перед отправкой предусмотрена короткая пауза обработки
файла. [MAX: загрузка файлов](https://dev.max.ru/docs-api/methods/POST/uploads),
[MAX: отправка медиа](https://dev.max.ru/docs-api/use-cases/sending-messages/media).

`POST_STARTED` сохраняется **до начала загрузки**. Ошибка или неопределённый результат
загрузки/отправки оставляет событие для сверки; автоматической повторной отправки
или замены на сообщение без файла нет. Для `CONFIRMED` GET должен подтвердить чат,
бота, точный текст, message ID и единственное файловое вложение: его имя, размер
и SHA256 скачанного содержимого. Одна совпавшая подпись без нужного файла недостаточна.
Этот путь проверен на имитации MAX; живая отправка в рамках подготовки не выполнялась.

Поддержка также может получить полный список из того же зафиксированного события.
Для сообщений без файла оператор передаёт короткий номер обращения и полный ID
отчёта. Поддержка проверяет полное совпадение ID; короткий префикс нельзя использовать
при неоднозначном результате поиска.

Для S3 найти событие по префиксу имени `<номер-обращения>`, выгрузить конкретный
`<полный-event_id>.json` обычным разрешённым read-only способом и выполнить:

```sh
python -m xtrek.terminal_feedback_messages --event-json event.json > details.txt
```

Для SQLite (открывается только `mode=ro`, без миграций и создания файла):

```sh
python -m xtrek.terminal_feedback_messages --sqlite /path/to/terminal.sqlite3 --reference 0123456789abcdef > details.txt
```

Команда прекращает работу при отсутствии или неоднозначности префикса. Каждый
номер в details.txt находится на отдельной строке. Исходный report/productionOrder
не перечитывается, поэтому поздняя замена отчёта не подменяет доказательства.

## Нужна ли модель

Для приведённых сочетаний модель не нужна: правила определяют причину и действие,
а шаблоны обеспечивают точные номера и числа без сетевой задержки и платы за API.
Сначала стоит измерить долю сообщений, которым оператору не хватает объяснения.

Варианты последующего согласования:

| Вариант | Задержка и стоимость | Оценка |
| --- | --- | --- |
| Детерминированные шаблоны | Локальный рендер, ноль затрат на модель | Реализовано, основной путь |
| Внешний API только для сложного объяснения | Сеть и токены; нужен выбранный провайдер, бюджет и правила обработки данных | Рассмотреть после пилота на обезличенных примерах |
| Локальная модель | Нет внешней передачи; нужны ресурсы и обслуживание, задержка зависит от оборудования | Имеет смысл только при уже доступной инфраструктуре |

Возможная точка интеграции — до фиксации `message_text` в drain, без доступа к
бизнес-функциям, статусам или транспорту. Только сочетания минимум трёх подтверждённых
классов, для которых шаблон остаётся непонятным по результатам пилота. Сбой API,
неизвестные статусы и нехватка фактов не являются поводом вызывать модель.

Проект ограничений: одна попытка, общий timeout 3 секунды, цель p95 добавочной
задержки ≤2 секунды (это требование к пилоту, не измеренная скорость модели).
Без повторов вызова внутри отправки, без фонового редактирования уже зафиксированного
текста. При ошибке, timeout, отказе, неполном ответе или нарушении проверки — тот же
детерминированный шаблон. Ограничение выдачи 150 токенов и объяснения 240 символов.

Модель получает только enum причин, счётчики и непрозрачные ссылки на группы фактов.
Полные ID, SSCC, КИ, криптохвосты, токены, подписи, оператор и chat_id ей не нужны.
Номера/числа и единственное разрешённое действие вставляет код после генерации.
Выход: структурированный объект с объяснением и ссылками на использованные факты.
Схема не доказывает истинность текста: Structured Outputs обеспечивает форму,
но возможны содержательные ошибки, отказ или неполный ответ. Нужны отдельные
проверки и fallback. [Официальная документация OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

Проверки перед сохранением: точный набор обязательных ссылок на факты, неизменность
чисел и идентификаторов после подстановки, отсутствие новых чисел/номеров и
инструкций в объяснении, одно действие из rule_id, максимум 6 строк и 3500 символов.
Свободный текст нельзя надёжно проверить одной JSON-схемой: до отдельной оценки
качества безопаснее разрешать только выбор утверждённых объяснений. В этом режиме
выгода модели невелика — ещё один аргумент начать с шаблонов.

Бюджет считается после выбора модели: `N × (Tin × Pin + Tout × Pout) / 1_000_000`,
где N — число сложных случаев, Pin/Pout — цены за миллион токенов. При проектном
лимите 800 входных и 150 выходных токенов 1000 случаев потребуют до 0,8 млн входных
и 0,15 млн выходных токенов. Например, при **условных, не тарифных** ценах $1/$4 это
$1,40 за 1000 случаев, без дополнительных расходов. Реальная цена, retention,
регион, доступность, лимиты и p95 проверяются после выбора провайдера и модели.
Автоматическое подключение модели, оплата или передача данных этой задачей не разрешены.
