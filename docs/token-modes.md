# Режимы работы с токенами

`TokenProcessor` работает в одном из двух режимов.

## Клиентский режим

`tokens_read_only=true` включён по умолчанию. `tokens_path` обязан указывать на
объект S3. Первый `TokenProcessor` в процессе скачивает `tokens.json`, проверяет
его и хранит снимок только в памяти. Остальные экземпляры в том же процессе
используют этот снимок без дополнительных запросов S3. Новый запуск CLI создаёт
новый процесс и обязательно получает новый снимок.

В Celery снимок очищается перед и после каждой задачи. Первый `TokenProcessor`
внутри задачи загружает актуальный объект S3, последующие используют тот же
снимок. Обновление токенов между задачами не требует перезапуска worker.

При автоматическом выборе токена проверка отчётов в `utils.py` определяет ИНН
для каждого отчёта и создаёт API-клиенты без глобального кэша токенов и клиентов.
Явно переданные клиентом API/NK-объекты и `TRUE_API_TOKEN` сохраняют приоритет;
за актуальность явно переданных токенов отвечает вызывающий код.

В этом режиме локальный `tokens.json` не читается и не используется при ошибке
S3. Методы публикации и `save_token()` запрещены. Клиентский код также не должен
вызывать `get_new_token()`.

## Серверный режим

Единственный контур выпуска токенов должен создавать процессор явно:

```python
TokenProcessor(tokens_read_only=False)
```

Перед изменением сервер обязательно читает актуальный объект S3. После выпуска
токена он сохраняет полный совместимый `tokens.json` и публикует его в S3.
Рекомендуемый запас обновления задаётся параметром
`tokens_refresh_before_expiry_seconds` (по умолчанию — 1800 секунд).

## Время

JWT `exp` трактуется как UTC и является авторитетным сроком JWT. Значения
`ДействуетС` и `ДействуетДо` с `Z` или offset используют указанную временную
зону. Исторические значения без зоны трактуются как `Europe/Moscow`. Формат
`tokens.json` при этом не меняется.

Штатные операции TokenProcessor журналируются на уровне `DEBUG`. На `INFO`
остаются только значимые события выпуска/публикации и принудительного обновления
после отказа авторизации; значения токенов не журналируются.

## Запуск мастера по расписанию

`python -m xtrek.token_worker --once` выполняет один цикл и завершается;
без аргументов поведение такое же. Внутреннего бесконечного цикла и sleep нет.
Мастер использует `tokens_read_only=False` независимо от клиентского значения
конфигурации. Актуальные токены не перевыпускаются. Отсутствующие, истекающие
или не имеющие определимого срока токены обновляются через штатную подпись.

`tokens.json` не удаляется. Перед сохранением каждой записи перечитывается S3;
публикуется весь набор с заменой соответствующего токена. Если источник S3
недоступен, обновление не начинается. Неудача получения/сохранения хотя бы
одного токена даёт код завершения 1; успешный цикл, включая отсутствие
необходимости обновления, — 0. Ошибка одной записи не мешает проверке остальных.

Для VPS в `deploy/systemd` подготовлены service и timer. Таймер запускает
мастера в минуты 00, 10, 20, 30, 40, 50. `Persistent=true` выполняет пропущенный
запуск после включения VPS. Активный oneshot-сервис не запускается повторно;
`flock` защищает запуск с тем же lock-файлом, тайм-аут сервиса — 9 минут.
При ошибке следующая попытка будет по расписанию. Запас 30 минут оставляет
время на подпись и повторную попытку до истечения токена.

Пути в unit-файле привязаны к рабочему VPS. Перед установкой нужно создать
`~/.cache/xtrek`, разместить код и направить `token-worker-current` на его
каталог. Конфигурация и подпись используются существующие. Celery остаётся
на независимом релизе main, останавливать его для штатного обновления токенов
не требуется. На одном источнике должен работать один мастер; старые
обновляторы и задания с удалением tokens.json должны быть отключены.

Ручной запуск: `sudo systemctl start xtrek-token-worker.service`.
Включение расписания: `sudo systemctl enable --now xtrek-token-worker.timer`.
Проверка: `systemctl list-timers xtrek-token-worker.timer` и
`journalctl -u xtrek-token-worker.service`.
Не используйте прежний `tw.sh`, удаляющий файл токенов.

На производственном VPS настройка `tokens_allowed_inns` содержит три рабочих
ИНН: `7733154124`, `9718180660`, `9723161905`. При её наличии обновляются только
перечисленные организации; отсутствие любой из них считается ошибкой цикла.
Это исключает случайное обновление тестовых организаций из общего каталога S3
без удаления их записей. Без настройки проверяются все найденные организации.
Старый `~/tw.sh` на VPS заменяется совместимым вызовом systemd-сервиса, чтобы
случайный ручной запуск больше не удалял токены и не останавливал Celery.
