# Ввод в оборот по готовой эмиссии

## Контракт

Одна входящая папка `Задания/` принимает два JSON-объекта. Тип определяется содержимым,
а не именем. Поле `codes` означает файл кодов; `Gtin` и `PasportData` — задание.
Смешение двух форматов отклоняется. Отдельного обработчика или очереди для этого
бизнес-маршрута нет.

- `<orderId СУЗ>.json`: `codes`, `orderId`, необязательные `blockId` и `omsId`.
- `<UUID документа 1С>.json`: обычное задание с `directMode: true`,
  `emissionDocumentId: <orderId СУЗ>`, точным `Quantity`, GTIN и паспортом.

Это два разных имени. `emissionDocumentId` обозначает **заказ СУЗ**, а не ссылку на
документ или вложение 1С. Внешняя обработка сохраняет происхождение в
`source1cEmissionId` и `source1cAttachmentName`.

В 1С проверено 15.10.2026: UUID ссылки документа, UUID ссылки вложения, UUID имени
вложения и `ИдентификаторЗаказа` различны. Менеджер
`СУЗПрисоединенныеФайлы.ДобавитьЗаписьВПротоколОбмена` присваивает имени новый
случайный UUID. Поэтому экспорт явно переименовывает кодовый файл в `orderId.json`.

## Обработка

1. Событие файла кодов само по себе не запускает бизнес-действий.
2. Задание нормализуется в `productionOrders/T-direct-<UUID задания>.json`.
   Тип UNIT/SET определяется общим `get_product_info_robust`: `feedProduct`,
   затем резервный `product_info`. Для directMode требуется явный булев признак
   `is_set`; тип из входящего задания не считается подтверждением каталога.
   Отсутствие парного файла вызывает повторную попытку стандартного worker.
3. Проверяется совпадение `orderId`, GTIN, количества, дат, отсутствие дублей и
   полный код химии с GS перед AI 93. Публикация в `kodes/<orderId>.json` выполняется
   условной записью `If-None-Match: *`.
4. В том же объекте сохраняются `productionOrderId`, `directMode` и отпечаток
   неизменяемого задания. Повтор с тем же содержимым допустим; другая привязка,
   коды или паспорт под тем же именем вызывают конфликт. Старый объект `kodes`
   без этой привязки не присваивается автоматически новому заданию.
5. Обычные `create_utilisation_task` и `sign_and_send_utilisation` готовят и отправляют
   нанесение. Для UNIT после `SUCCESS` используются `create_introduce_task` и
   `sign_and_send_introduce`. После `CHECKED_OK` производственное задание получает `check=finished`.
   Сбой записи отметки повторяет проверку статуса, не отправку документа.
6. Для SET существующая `create_virtual_production_tasks` создаёт задания на
   компоненты по составу НК и количеству кодов набора. Компоненты проходят штатные
   эмиссию, нанесение и ввод в оборот; наследуют производителя и даты родителя.
   Общая `set_ready_check` ждёт успешного нанесения набора и ввода всех компонентов.
   Затем `create_equipment_set_report` собирает виртуальные наборы из файлов эмиссии
   через существующий генератор, а стандартные функции готовят и отправляют
   SETS_AGGREGATION. Подтверждённый `CHECKED_OK` завершает прямое задание
   с той же отметкой `check=finished`, что и UNIT.
   Прямой ввод самого SET как UNIT запрещён проверкой перед отправкой.

Печать, задания оборудования и транспортная агрегация не запускаются.
Для исходных кодов UNIT/SET не требуется новая эмиссия, файл `emissions` или
`emissionOrders`; для виртуальных компонентов SET используется штатная новая эмиссия.
Общие функции
поддерживают связь с производственным заданием через готовый файл `kodes`.
Перед публикацией и подписанием документа повторно проверяются его состав,
производитель и даты. Существующие задания на нанесение не переписываются.

## Первая версия и даты

Один полностью полученный заказ, один принятый входящий блок в 1С, один GTIN,
от 1 до 30 000 уникальных кодов. Несколько вложений, частей и неполная выгрузка
отклоняются. Разбиение по блокам требует следующей версии идентичности:
нельзя записывать несколько независимых файлов под одним `orderId`.

Источники: основание эмиссии `ЗаказНаПроизводство.ПроизводственнаяСерия`:
`ПланируемаяДатаПроизводства` → `Batch_date_production`,
`СрокОкончанияГодности` → `Batch_date_expired`. В выгрузке даты имеют ISO-формат.
Пользователь подтверждает фактическую дату производства и срок годности перед
выгрузкой: плановая дата серии сама по себе не доказывает фактическое производство.
Дата документа эмиссии и текущая дата не подставляются вместо этих значений.

Лимиты проверены по имеющейся документации: API СУЗ 3.0.40 (ред. 67, 24.09.2026),
GET `/api/v3/codes` — до 150 000 за запрос, отчёт о нанесении — до 30 000;
True API v707 — до 30 000 кодов и 30 МБ на документ. Отдельный байтовый лимит
СУЗ не подтверждён. На подготовленные документы установлена консервативная граница
30 000 000 байт. Значение `alcoholVolume` берётся из паспорта или существующей
настройки группы chemistry, без изменения старых документов.

## Выгрузка 1С

Исходники внешней обработки находятся в `integrations/1c`. Конфигурация базы не
меняется. Кнопка «Проверить» только читает данные; «Выгрузить» публикует сначала коды,
затем задание в одну и ту же папку. Повторная подготовка использует стабильные имена.

- `local`: папка `1CExchange` на сервере 1С. Завершённый временный файл переименовывается
  без перезаписи. Совпадение существующих файлов проверяется по SHA-256.
  Действующий uploader имеет лимит 1 МиБ; обработка явно отклоняет более крупные
  файлы в этом режиме. До увеличения лимита uploader используйте `aws`/`function`.
- `aws`: установленный на Windows-клиенте 1С AWS CLI, именованный профиль, бакет и общий префикс.
  Используются `s3api get-object` и условный `put-object --if-none-match "*"`.
  Секреты не хранятся в обработке. Повтор и неоднозначный результат проверяются
  чтением и точным сравнением двоичного содержимого, а не перезаписью.
  Используется профиль текущего пользователя клиента; профиль службы 1С не нужен.
- `function`: существующий контракт POST `{file_name, folder}` → `upload_url`.
  PUT всегда условный. При HTTP 412 обработка использует `download_url` из ответа
  либо запрашивает его отдельным POST `{download: ключ}` — это действующий контракт
  bukupl. Затем сверяет SHA-256; другое содержимое вызывает конфликт.
  Входящий префикс должен уже существовать (иначе функция возвращает HTTP 400).

Локальный транспорт вызывает встроенный Windows PowerShell и System.IO.File.Move
без замены существующего файла; отдельные .ps1 и COM не используются. Эта обработка
предназначена для проверенного Windows-сервера WMS. Настройки транспорта не содержат
промышленных адресов по умолчанию. До отдельного разрешения не выгружать реальные
пары в папку, обрабатываемую действующим промышленным worker.

## Изолированная проверка

Сначала выполнить локальные тесты с подменёнными API/подписью. Следующий сетевой этап
требует отдельного разрешения на реальные отправки. Для него использовать:

- отдельные test-бакеты либо выделенный префикс одного test-бакета;
- `XTREK_S3_INPUT_BUCKET`, `XTREK_S3_INTERNAL_BUCKET`, `XTREK_S3_EVENT_PREFIX` у poller;
- совпадающие `input_bucket`, `internal_bucket`, `event_key_prefix` и все пути
  `suz_worker_config` у worker;
- отдельные RabbitMQ vhost/user/queue (`XTREK_LOCAL_BROKER_URL`,
  `XTREK_LOCAL_QUEUE_NAME`), отдельный `XTREK_S3_POLL_LEDGER` и `operation_state_path`;
- явные `XTREK_S3_CUTOFF_UTC` и `XTREK_LOCAL_ALLOWED_INNS`, без исторического replay;
- scanner и publisher из существующего `xtrek.s3_poller`, worker из `xtrek.tasks`.

Тестовые службы не подключаются к промышленной очереди и не используют её outbox.
Продакшен не обновляется из этой ветки; выпуск — только полным проверенным `main`.

## Сквозная проверка без отправок

16.10.2026 на Selectel Edith подготовлена отдельная служба
`xtrek-direct-synthetic.service`, user/vhost/queue `xtrek_direct_synthetic`.
Штатные poller, outbox, Celery/router и подготовка документов проверены на реальном
тестовом S3, с подменёнными внешними API и подписью: 6 событий + 6 повторов успешно.
После теста служба остановлена, автозапуск не включён.

Дополнительно SET проверен локальным сквозным тестом с настоящими функциями подготовки,
LocalStorage и генератором наборов; внешние ответы заменены синтетическими, сеть
заблокирована. Это отдельная проверка бизнес-цепочки, без облачного poller/RabbitMQ.
Воспроизводимый сценарий: [test_direct_set_chain.py](../../tests/test_direct_set_chain.py).

Затем SET успешно прошёл существующий тестовый S3 и изолированные RabbitMQ/worker
на Edith: 3 набора состава 2+1, 20 событий и 20 повторов без повторных отправок.
Внешние API и подпись подменены; worker после проверки остановлен, очередь пуста.

Стресс-прогон: 15 эмиссий по 30 000 кодов (450 000 всего) через тестовый S3,
изолированные RabbitMQ и worker; внешние API подменены. Все задания завершены,
повторная доставка не вызвала дополнительных отправок. Это проверка обработчика,
а не производительности формы 1С или реальных API.


## Результат реального прогона и ревью

16.10.2026 в изолированном тестовом S3/RabbitMQ/worker выполнен подтверждённый
пользователем прогон против реального API: 1 UNIT, 3 SET, 6 компонентов двух GTIN.
Нанесение завершилось SUCCESS, три документа ввода и документ агрегации наборов —
CHECKED_OK. Независимая проверка cises/info подтвердила INTRODUCED всех кодов,
по одному компоненту каждого GTIN в каждом наборе, уникальность вложений и parent-ссылки.
Токены использовались без обновления; после прогона worker остановлен, очередь пуста,
временный доступ CryptoPro снят. Промышленный обработчик не обновлялся.

Во время ревью добавлена отсутствовавшая отметка завершения прямого UNIT.
Регрессионные тесты проверяют запись отметок UNIT/SET, повтор после ошибки хранилища,
сохранение существующих тегов и отсутствие завершения для неподтверждённых документов.
Эта корректировка проверена локальными тестами; реальный прогон ради отметки не повторялся.

Общая отметка «Выгружено» в обработке 1С означает доставку обоих файлов, а не ввод
в оборот. Она хранится в общей папке журнала отдельно от статуса worker в S3.
