# Пункт 4: локальные регрессии миграции токенов

Дата: 14.09.2026. Ветка: `feature/token-purpose-model`.
Результат: **175 тестов и 14 вложенных проверок пройдены**, 20 тестовых модулей.
К 148 тестам этапа реализации добавлено 27 регрессионных сценариев.

## Воспроизводимый запуск

Из корня репозитория, в Python-окружении с зависимостями проекта, pytest и Celery:

```sh
python tools/run_token_regressions.py
```

Фактически использовано изолированное окружение `/private/tmp/xtrek-token-tests`,
Python 3.14. Скрипт запускает фиксированную подборку тестов, удаляет из своего
окружения переменные рабочих токенов/облачной авторизации и блокирует реальные
соединения через `socket.connect/connect_ex` до сбора тестов. HTTP, SignJS и S3
подменены локальными тестовыми реализациями. Скрипт не устанавливает зависимости
и не меняет настройки родительского shell.

## Проверенное поведение

| Область | Проверка и результат |
|---|---|
| Порядок записей | Все 6 перестановок JWT, UUID True API и UUID СУЗ, отдельно при обновлении каждого назначения. Результат публикации одинаковый. |
| Независимость | Обновляется только истекающая запись выбранного назначения. JWT, другая организация и sandbox сохраняются. UUID True API и UUID СУЗ намеренно имеют одинаковую строку в исходных тестовых данных. |
| Сроки | Управляемое время: 1801 секунда — пропуск, 1800 — обновление; проверены 1, 0 и −1 секунда до окончания срока. Формат и срок берутся из одной записи. |
| Повторный цикл | Сразу после успешного обновления второй цикл не перевыпускает токен и не публикует файл повторно. |
| Полный цикл | Настоящие функции генератора, проверки, мастера и TokenProcessor проходят через подменённые HTTP/подпись/S3; успех проверки разрешает публикацию, HTTP 401 запрещает её. |
| Отказ публикации | Старый S3-источник сохраняется, блокировка освобождается. Новый клиент игнорирует оставшийся локально кандидат и читает S3; после успешного восстановления перечитывает новое значение. Проверены оба назначения. |
| Повреждённый источник | Ошибка повторного чтения не разрешает работу с неподходящим реестром и не портит следующий снимок; после восстановления S3 чтение возобновляется. |
| Долгоживущий процесс | Две eager-задачи Celery в одном PID используют реальные обработчики task_prerun/task_postrun. Между задачами мастер публикует UUID; следующая задача получает новый Bearer, сохраняя прежний clientToken СУЗ. Проверены успешная и аварийная первая задача. |
| Совместимость | Повторно пройдены legacy/v2, CLI, linked GTIN, проверки отчётов, эмиссия, ввод, операции агрегации, сведения о КИ и защита от повторной отправки документов. |

## Найденная и исправленная ошибка

`save_record` проверял срок лишь перед перечитыванием S3. Если токен истекал за время
чтения, он всё равно записывался и публиковался. Новый тест сначала воспроизвёл ошибку:
**1 failed, 23 passed**.

Добавлены проверки срока после перечитывания источника и после локальной записи,
непосредственно перед отправкой в S3. Истёкший кандидат отклоняется; при ошибке после
локальной записи восстанавливается прежний снимок в памяти. Два отдельных теста
проверяют задержку чтения и задержку записи. Это не продлевает срок токена и не
гарантирует его действительность после произвольно долгой сетевой отправки.

## Границы результата

Это локальная проверка кода. Eager Celery проверяет границы задач в одном процессе,
но не заменяет испытание реального долгоживущего worker с брокером. Реальная
криптографическая подпись, серверная проверка CRPT, доступность S3 и рабочий SignJS
здесь не проверялись. Сертификаты и рабочие токены не использовались; production,
очереди и службы не менялись.

Для следующего пункта 5 остаётся отдельное испытание для согласованной организации:
изолированное хранилище/процесс, свежий UUID, обновление и подхват настоящим Celery
без перезапуска. Производственное переключение относится к пункту 6.
