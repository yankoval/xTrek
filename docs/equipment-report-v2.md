# Формат отчёта оборудования xTrek v2

Статус: целевой формат для внедрения  
Версия формата: `2`  
Дата: 2026-07-31

Связанные файлы:

- [JSON Schema](schemas/equipment-report-v2.schema.json);
- [пример UNIT](examples/equipment-report-v2-unit.example.json);
- [пример SET](examples/equipment-report-v2-set.example.json);
- [назначение SSCC паллетов в задании оборудования](equipment-task-palletization-v2.md).

## 1. Назначение

Отчёт v2 передаёт фактически сформированную оборудованием транспортную
иерархию:

```text
паллет -> короб -> UNIT или SET
```

Один отчёт может содержать несколько закрытых паллетов. Каждый короб находится
внутри ровно одного паллета, а каждый товарный код — внутри ровно одного
короба.

SSCC паллетов выделяются заранее при формировании задания оборудования. Отчёт
не создаёт новые SSCC и может использовать только значения, перечисленные в
`palletNumbers` исходного задания.

Для True API из отчёта формируется один `AGGREGATION_DOCUMENT`: сначала связи
товарных кодов с коробами, затем связи коробов с паллетами.

## 2. Общая структура

```json
{
  "schemaVersion": 2,
  "id": "T-EXAMPLE-UNIT-20260729-0001",
  "startTime": "2026-07-29T08:00:00Z",
  "endTime": "2026-07-29T08:30:00Z",
  "operator": "operator-1",
  "operators": ["operator-1"],
  "model": "equipment-model",
  "build": "2.0.0",
  "readyPallet": [
    {
      "Number": 0,
      "palletNumber": "000000000000000017",
      "palletAggregate": true,
      "palletTime": "2026-07-29T08:30:00Z",
      "readyBox": [
        {
          "Number": 0,
          "boxNumber": "000000000000000024",
          "boxAgregate": true,
          "boxTime": "2026-07-29T08:10:00Z",
          "productNumbers": [
            "010460000000000121EXAMPLE01"
          ],
          "productNumbersFull": [
            "010460000000000121EXAMPLE01\u001d93ABCD"
          ]
        }
      ]
    }
  ],
  "sampleNumbers": [],
  "sampleNumbersFull": null,
  "defectiveCodes": null,
  "defectiveCodesFull": null,
  "emptyNumbers": null
}
```

Иерархия задаётся вложенностью объектов. Отдельный плоский список коробов и
ссылки на него не используются.

## 3. Корневые поля

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `schemaVersion` | integer | да | Всегда `2`. Наличие `readyPallet` без этого поля является ошибкой. |
| `id` | string | да | Уникальный идентификатор отчёта. Рекомендуется использовать идентификатор задания оборудования. |
| `readyPallet` | array | да | Непустой массив закрытых паллетов. |
| `startTime` | string/null | нет | Начало выполнения задания в ISO 8601. |
| `endTime` | string/null | нет | Завершение отчёта в ISO 8601. |
| `operator` | string/null | нет | Основной оператор. |
| `operators` | array[string] | нет | Все операторы, участвовавшие в выполнении задания. |
| `model` | string/null | нет | Модель или идентификатор оборудования. |
| `build` | string/null | нет | Версия приложения оборудования. |
| `sampleNumbers` | array[string] | нет | Короткие коды отобранных образцов. Не входят в агрегацию. |
| `sampleNumbersFull` | array[string]/null | нет | Полные коды образцов. |
| `defectiveCodes` | array[string]/null | нет | Короткие отбракованные коды. Не входят в агрегацию. |
| `defectiveCodesFull` | array[string]/null | нет | Полные отбракованные коды. |
| `emptyNumbers` | array[string]/null | нет | Зарезервированное поле старого формата. |
| `compatibility` | object | нет | Метаданные системного преобразования отчёта v1 в v2. Оборудование это поле не формирует. |

Дополнительные корневые поля разрешены для обратной совместимости. Они не
должны изменять смысл обязательных полей.

## 4. Объект паллета

Путь: `readyPallet[]`.

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `palletNumber` | string | да | Заранее назначенный в задании SSCC паллета: ровно 18 цифр, без идентификатора применения `00`. |
| `palletAggregate` | boolean | да | Всегда `true`: физический состав паллета закрыт и больше не изменяется. Поле не является результатом контрольного сканирования. |
| `readyBox` | array | да | Непустой массив закрытых коробов паллета. |
| `Number` | integer | нет | Локальный порядковый номер паллета, начиная с `0`. Не является идентификатором. |
| `palletTime` | string/null | нет | Время закрытия паллета в ISO 8601. |

В итоговый отчёт нельзя включать открытый паллет. Промежуточное состояние
оборудования хранится отдельно и не загружается как финальный отчёт.

Каждый `palletNumber` должен присутствовать в `palletNumbers` исходного
задания. Назначенный, но фактически не использованный SSCC в отчёт не
включается.

`palletNumber` обозначает физический паллет на уровне бизнес-процесса. В True
API физические короб и паллет могут возвращаться с одинаковым
`generalPackageType=BOX`; уровень определяется связями вложенности.

## 5. Объект короба

Путь: `readyPallet[].readyBox[]`.

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `boxNumber` | string | да | SSCC короба: ровно 18 цифр, без идентификатора применения `00`. |
| `boxAgregate` | boolean | да | Всегда `true`: короб закрыт и больше не изменяется. Имя поля сохраняет историческое написание. |
| `productNumbersFull` | array[string] | да | Непустой массив полных кодов маркировки с криптохвостом. |
| `productNumbers` | array[string] | нет | Те же коды без криптохвоста. Если поле передано, оно должно точно соответствовать `productNumbersFull` по количеству, порядку и значениям после удаления криптохвоста. |
| `Number` | integer | нет | Локальный порядковый номер короба внутри паллета, начиная с `0`. |
| `boxTime` | string/null | нет | Время закрытия короба в ISO 8601. |

В итоговый отчёт нельзя включать пустой или открытый короб.

## 6. Представление кодов маркировки

### Полный код

`productNumbersFull` хранит строку, полученную оборудованием, без потери
криптохвоста. Разделитель GS (ASCII 29) в JSON кодируется как `\u001d`:

```json
"010460000000000121EXAMPLE01\u001d93ABCD"
```

Оборудование не должно:

- заменять GS видимыми символами, пробелом или строкой `<GS>`;
- удалять криптохвост;
- добавлять кавычки, скобки или префикс сканера внутрь кода.

### Короткий код

`productNumbers` содержит часть полного кода до первого GS:

```text
010460000000000121EXAMPLE01
```

Поле необязательно, потому что xTrek может получить его из
`productNumbersFull`. Если оборудование его передаёт, любое несовпадение
считается ошибкой всего отчёта.

### SSCC

В отчёте SSCC хранится как 18 цифр:

```text
000000000000000024
```

Перед отправкой в True API xTrek добавляет AI `00`:

```text
00000000000000000024
```

Оборудование не должно самостоятельно добавлять AI `00`. SSCC должен быть
получен из согласованного источника и иметь корректную контрольную цифру.

## 7. Правила целостности

Проверки выполняются для отчёта целиком:

1. `schemaVersion` равен `2`.
2. Есть хотя бы один паллет, в каждом паллете есть хотя бы один короб, в каждом
   коробе есть хотя бы один товарный код.
3. `palletAggregate` и `boxAgregate` равны `true`.
4. Все SSCC паллетов и коробов уникальны; один SSCC нельзя использовать
   одновременно как паллет и короб.
5. Короб встречается только в одном паллете.
6. Короткий товарный код встречается только один раз во всём отчёте.
7. Если передано `productNumbers`, оно точно соответствует
   `productNumbersFull`.
8. Количество коробов в паллете соответствует нормативу задания.
9. Неполный последний паллет допускается только по правилу задания и только
   после явного закрытия оператором или управляющей системой.
10. Каждый SSCC паллета входит в `palletNumbers` исходного задания
    оборудования.

Повторная загрузка того же `id` должна передавать тот же состав и те же SSCC.
Изменять закрытые короб или паллет при повторе запрещено.

## 8. UNIT и SET

Структура отчёта одинакова для обоих типов товара. Отличается смысл элементов
`productNumbersFull`.

### UNIT

В коробе перечисляются коды отдельных товарных единиц. После успешного ввода
товара в оборот xTrek формирует связи:

```text
UNIT -> короб -> паллет
```

### SET

В коробе перечисляются коды готовых наборов (`SET`), нанесённые на упаковки
наборов. Коды компонентов набора в этот отчёт не включаются.

xTrek сначала отдельным этапом создаёт состав каждого набора и ожидает его
успешного завершения. Затем по отчёту v2 формирует транспортные связи:

```text
компоненты -> SET        отдельный этап
SET -> короб -> паллет   один транспортный AGGREGATION_DOCUMENT
```

## 9. Назначение SSCC, закрытие и контрольное сканирование

Управляющая система передаёт оборудованию норматив количества коробов в
паллете и достаточное число заранее выделенных SSCC. Рекомендуемый процесс:

1. процедура формирования задания проверяет `numBoxesInPallet`;
2. при наличии норматива процедура рассчитывает
   `ceil(Quantity / numBoxesInPallet)`, добавляет настраиваемый страховой запас
   и заранее выделяет итоговое число SSCC;
3. выделенные SSCC сохраняются в `palletNumbers` задания;
4. оборудование последовательно использует только назначенные SSCC;
5. оборудование закрывает короба и распределяет их по паллетам;
6. при достижении норматива закрывает паллет, а для неполного последнего
   паллета запрашивает явное разрешение;
7. после закрытия последнего паллета формирует неизменяемый отчёт v2;
8. Yandex Serverless Function получает событие загрузки отчёта и отправляет в
   MAX сводку и изображение SSCC для каждого паллета;
9. оператор печатает ярлык, наклеивает его и сканирует SSCC;
10. принимающая сканирование процедура сравнивает код с назначенным
   `palletNumbers` и паллетами отчёта;
11. после подтверждения всех паллетов отчёт допускается к обработке xTrek.

Отчёт описывает факт упаковки. xTrek не должен автоматически перераспределять
короба между паллетами.

Контрольное сканирование хранится как отдельное состояние обработки, а не как
поле отчёта v2. Это позволяет оставить `palletAggregate: true` совместимым с
согласованным контрактом и не изменять уже загруженный неизменяемый отчёт.
Повторное сканирование того же SSCC идемпотентно. Сканирование SSCC другого
задания или другого паллета отклоняется и не открывает обработку отчёта.

## 10. Совместимость с v1

Отчёт без `schemaVersion`, имеющий корневой `readyBox`, считается v1.

xTrek преобразует его в канонический v2 по правилу «все короба отчёта в один
паллет». Если в производственном задании отсутствует `numBoxesInPallet`,
заранее выделяется ровно один SSCC паллета. Он сохраняется в `palletNumbers`
задания, `reportSchemaVersion` устанавливается в `1`, и SSCC повторно не
выделяется обработчиком отчёта. Если в старом задании SSCC не был
назначен, сохраняется прежнее поведение «только короба» до отдельного
переключения миграционного режима. Исходный файл v1 остаётся неизменным для
аудита.

Системная каноническая копия может содержать:

```json
{
  "compatibility": {
    "convertedFromSchemaVersion": 1,
    "strategy": "single-pallet",
    "sourceReportId": "legacy-report-id"
  }
}
```

Оборудование, поддерживающее v2, не должно создавать поле `compatibility`.

## 11. Обработка ошибок

Отчёт отклоняется целиком при структурной ошибке, дублировании или нарушении
иерархии. Частичная агрегация корректной части отчёта не выполняется.

До исправления отчёта обработчик не должен:

- запрашивать новые SSCC взамен назначенных в задании;
- переносить короб в другой паллет;
- удалять дублирующийся товарный код;
- считать открытый объект закрытым.

Сообщение обратной связи должно содержать `id` отчёта и точный путь ошибочного
поля, например:

```text
readyPallet[0].readyBox[1].productNumbersFull contains a duplicate product code
```

## 12. Область поддержки в xTrek

Модуль `xtrek.aggregation_builder` уже принимает v2 и строит многоуровневый
`AGGREGATION_DOCUMENT`.

До переключения оборудования на v2 остальные потребители отчёта в обработчике
должны быть переведены с прямого чтения корневого `readyBox` на единый
канонический адаптер. До завершения этой миграции формат v2 нельзя включать в
рабочем контуре только на основании поддержки транспортной агрегации.

Отдельная утилита создания состава SET, `KinReportGenerator` и внутренний
формат `equipment_set_reports` не входят в эту миграцию и не изменяются без
отдельного прямого согласования.
